## What changed (verified by direct diff read, file by file)

**PostgreSQL isolation model corrected further:**
- `governance_app` no longer owns `polynovea_governance` — the bootstrap
  admin does; `governance_app` owns only the `governance` schema
  (`CREATE SCHEMA governance AUTHORIZATION governance_app`, no `OWNER`
  clause on `CREATE DATABASE`).
- The prior design's `REVOKE CONNECT ON DATABASE polynoveacrm FROM
  governance_app` is removed. **This was a real, substantive flaw in the
  design this session shipped in `4777761`, correctly caught by this
  audit**: PostgreSQL privilege resolution is additive — a role has a
  privilege if it holds it directly *or* via `PUBLIC`. `governance_app`
  was never granted `CONNECT` directly (its access, if any, would only
  ever have come from `PUBLIC`'s default), so revoking it specifically
  from `governance_app` was a no-op with no actual isolating effect.
  Independently confirmed correct against PostgreSQL's documented
  privilege model (`GRANT`/`REVOKE` semantics, `PUBLIC` pseudo-role
  behavior) — this session's own `4777761` claim that the revoke "proves
  isolation" was wrong.
- New `backend/provisioning/002_verify_cross_database_isolation.sql`:
  read-only, uses `has_database_privilege()`/`has_table_privilege()`/
  `has_function_privilege()` — the correct Postgres functions for
  *effective* privilege (they account for `PUBLIC` and role membership,
  unlike inspecting `pg_database.datacl`/`pg_class.relacl` directly, which
  only shows explicit grants). Fails closed (`RAISE EXCEPTION`) if
  `governance_app` can effectively `CONNECT` to `polynoveacrm`, holds any
  administrative role attribute, or has any role membership. Contains no
  `GRANT`/`REVOKE`/`CREATE`/`ALTER`/`DROP`/DML statement anywhere —
  confirmed by direct read and by
  `test/provisioning/governanceProvisioningContract.test.ts`'s own
  read-only assertion.
- For the *new* `polynovea_governance` database (not the shared one), the
  provisioning script does correctly lock down `PUBLIC`: `REVOKE ALL ON
  DATABASE polynovea_governance FROM PUBLIC` followed by an explicit
  `GRANT CONNECT ... TO governance_app` — safe here because the database
  is brand-new with no other connections or dependents at creation time,
  unlike a blind revoke against the shared, live `polynoveacrm`.
- The script deliberately does **not** attempt to harden `polynoveacrm`'s
  own `PUBLIC` posture — correctly recognizing that doing so blindly could
  break legitimate existing access, and that the correct remediation
  (inventory legitimate roles, revoke `PUBLIC`, explicitly re-grant) is a
  separately-reviewed production ACL change, not something to embed in a
  one-time bootstrap script.
- `ALTER ROLE governance_app SET search_path` is now
  `IN DATABASE polynovea_governance`, not global — narrower blast radius
  if the credential were ever misconfigured to connect elsewhere.
- Password handling moved from a committed placeholder literal
  (`CHANGE_ME_BEFORE_RUNNING...`) to a required psql variable
  (`:'governance_password'`, with an explicit `\if :{?governance_password}`
  guard that refuses to run without it) — removes the risk of the script
  being run unmodified with a known weak password.

**Migrations hardened:**
- `migrationRunner.ts`'s `runMigrations()` now applies each migration
  file inside a real transaction on one pinned `pg.PoolClient`
  (`PgDbClient.transaction()`, new on the `DbClient` interface) —
  `BEGIN`/work/`COMMIT`, `ROLLBACK` + rethrow on failure, `client.release()`
  in `finally`. This correctly fixes the "not transactional" limitation
  `4777761`'s own status doc had flagged as a known gap: a sequence of
  `pool.query()` calls (the old approach) is not a transaction, because
  each call may be served by a different pooled connection.
- Each migration's own SQL text is now sent as a single multi-statement
  query on that pinned connection, removing the hand-rolled
  `splitStatements()` line-comment/semicolon splitter — a real
  simplification, since that splitter could not have handled a future
  migration using dollar-quoting or a semicolon inside a string literal
  (both explicitly named as its limitation in `4777761`'s own comments).
- Applied migrations are now content-addressed with a SHA-256 checksum,
  stored in `governance.schema_migrations`. Editing an already-applied
  migration's file content now fails the next run with a hard error
  ("Migration checksum mismatch... Applied migrations are immutable") —
  verified by a new dedicated test
  (`db/migrationRunner.test.ts` "fails closed when an applied migration
  checksum no longer matches source").
- Minor observation, not a defect: `PgDbClient.transaction()` calls
  `client.release()` unconditionally in `finally`, including after a
  failed `ROLLBACK`. `pg`'s `release(err?)` can be told a client is
  broken so the pool discards rather than reuses it; a failed rollback in
  that rare case currently returns a possibly-inconsistent connection to
  the pool instead. Not exercised by any test, not a regression from
  `4777761` (which had no transaction handling at all), and not required
  by anything this pass asked for — flagged here as a documented,
  optional future hardening, not fixed in this pass to stay within the
  requested scope (inspect, verify, fix red, don't invent new work).

**Privileged authentication hardened:**
- `CognitoIdentityProvider.verifyToken()` now passes `algorithms: ["RS256"]`
  to `jose`'s `jwtVerify()`, explicitly restricting the accepted signing
  algorithm (defense against algorithm-confusion attacks — e.g. an
  attacker crafting a token signed with a different, weaker or
  attacker-controlled algorithm).
- Rejects any token whose `token_use` claim is not `"id"` — Cognito access
  tokens are signed by the same pool but carry `client_id` rather than a
  trustworthy `aud`, and must never be accepted by this operator boundary.
  New typed `WrongTokenUseError` (401), correctly returned as-is by
  `mapVerificationError` (checked first, before the generic `jose` error
  mapping) — confirmed by direct read that it is not swallowed or
  reclassified.
- `requireManagementApiAuth` now rejects an otherwise-valid, active
  operator whose directory record has `mfaEnrolled: false`
  (`OperatorMfaRequiredError`, 403) — closes the gap where a real, valid
  Cognito session for a non-MFA-enrolled operator could previously reach
  authorization checks at all.

**Fake step-up path disabled:**
- `POST /management/v1/session/step-up` no longer accepts or records any
  caller-asserted state — it unconditionally responds `501
  STEP_UP_NOT_CONFIGURED` (new `StepUpNotConfiguredError`).
- `requireStepUp()` additionally rejects a step-up record whose `method`
  is the literal `"skeleton-unverified"` string the old route used to
  write — so even a stale, previously-recorded fake step-up state from
  before this change cannot satisfy the check.
- Verified end-to-end: the rewritten
  `middleware/managementApiAuth.integration.test.ts` case posts to the
  disabled route (expects 501), confirms `STEP_UP_REQUIRED` still blocks
  the protected route afterward, then proves only step-up state written
  directly via `sessionStore.recordStepUp(...)` (standing in for a future
  real Cognito MFA challenge) — never through the HTTP route — can satisfy
  it.

**Express 4 async-rejection handling fixed:**
- Express 4 does not automatically forward a rejected promise from an
  async request handler to error-handling middleware (fixed in Express 5,
  not present here). `requireRole`/`requireScope`/`requireStepUp`
  (`authorize.ts`) and `/session/logout` (`routes/management/index.ts`)
  previously had `void` fire-and-forget async work with no ability to
  respond if it threw — now wrapped in `try`/`catch` calling `next(err)`.
  A new router-local `managementErrorHandler` (an Express
  `ErrorRequestHandler`) catches any forwarded `ManagementAuthError`
  (including `DatabaseUnavailableError`, which extends it), audits it as
  `authz.denied`, and returns the typed status/code/message — closing a
  real gap: `sessionStore`/`operatorDirectory` are now Postgres-backed
  (since `4777761`), so a DB failure *after* authentication (e.g. during
  logout) previously had no defined HTTP response path at all. Verified by
  a new test (`db/managementApiAuthDbUnavailable.integration.test.ts`,
  "returns typed 503 when the DB fails after authentication during
  logout") that injects a `DatabaseUnavailableError` from
  `sessionStore.revoke()` mid-request and confirms a clean `503
  GOVERNANCE_DB_UNAVAILABLE`, not a hang or an unhandled rejection.

**Bootstrap CLI hardened:**
- `scripts/bootstrapOperator.ts` no longer hardcodes `mfaEnrolled: true`
  for every created operator record. A new required `--mfa-verified` flag
  must be passed explicitly (`mfaEnrolled: args.mfaVerified`, and the
  script refuses to run at all without it) — the CLI can no longer
  silently claim MFA enrollment that was never actually verified.

**CI:**
- `.github/workflows/ci.yml`'s push trigger now includes `master` in
  addition to `main` (this repository's default branch is `master` — see
  `git log`/`git branch` — so the push trigger previously would not have
  fired on this repository's own default branch at all).

## What this pass does not, and cannot, establish

Everything above was verified by static analysis (diff read), unit/
integration tests, and pg-mem substitution — the same limitations already
documented in `docs/1A.3_status.md` apply unchanged: **no real Postgres
server is reachable from this session** (no AWS credentials, no local
Postgres/Docker). In particular:

- `002_verify_cross_database_isolation.sql`'s actual pass/fail behavior
  against the real `polynoveacrm` database has not been run — only its SQL
  correctness has been reviewed (correct use of `has_*_privilege()`
  functions, correct catalog joins, a hard-failing `DO` block).
- Neither provisioning script has executed against any real PostgreSQL
  server.
- The migration runner's real transactional behavior (`BEGIN`/`COMMIT`/
  `ROLLBACK` on a pinned connection) is proven against pg-mem and against a
  mocked `pg.Pool` (see `test/db/pgDbClient.test.ts`'s new `transaction()`
  cases), not against real PostgreSQL's actual transaction semantics.

1A.3 remains **NOT CLOSED**. This hardening pass improves the source/local
certification's correctness and closes real gaps found by direct Postgres
privilege-model review, but it does not substitute for the live
provisioning and effective-privilege certification `docs/1A.3_status.md`'s
own "Live certification required" checklist still requires.
