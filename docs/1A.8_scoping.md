## 1. Current legacy behaviour (ground truth, not assumption)

### 1.1 Commission (`POST /provision-tenant`, `provision.js:34-223`)

- Auth: `requirePlatformKey` only — a single shared static secret, no operator identity (confirmed non-negotiable-invariant #2 violation if reused as-is: "`requirePlatformKey` is not Phase 1A auth").
- Pre-check: if `send_invite && admin_email`, rejects with 409 if that email already belongs to another tenant (`app_users` join) — this is the *existing* cross-tenant-identity guard, and it is a pre-check, not a transactional guarantee (see §3.10).
- Transaction: `provision_tenant(name, slug, plan, industry, country, timezone)` SQL function (`078_fix_tenant_feature_seeding.sql:29-116`) — validates `plan` against `public.plans` (raises `Invalid plan: %` if unknown — this **is** the canonical plan source referenced by handoff §7), validates slug uniqueness (raises `Slug already taken: %`), inserts `tenants` row with `status = 'trial'`, `trial_ends_at = now() + 14 days` (not 30 days — a stale code comment at `provision.js:99` says "30-day DB default"; the real default is 14 days, confirmed from the SQL itself), inserts `subscriptions`, seeds 15 default `module_*` `tenant_features` rows (owner-side baseline default, not a desired-entitlement model — matches handoff §4.8), seeds `app_settings`/`onboarding_state`/a default `Leadership` team.
- `account_type: "live"` clears `trial_ends_at` and sets `status = 'active'` immediately, as a separate `UPDATE` after the transaction's own default. `trial_days` (when not `"live"`) overrides the 14-day default.
- `enabled_engines`/`enabled_integrations` (optional request body arrays) directly `UPDATE`/`INSERT` `tenant_features` rows — this is exactly the surface handoff §4.8 says 1A.8 must **not** reproduce (it belongs to 1A.9/1A.14).
- Best-effort holiday-calendar seed (`syncHolidayCalendar`) — explicitly non-fatal, logged and swallowed on failure, never rolls back the transaction. Matches handoff §4.11's "completed-with-warning" treatment exactly, already in the real code.
- Optional Cognito admin creation (`AdminCreateUserCommand`) — **only if `send_invite && admin_email`**, *after* the DB transaction has already committed. On `UsernameExistsException`, falls back to `AdminUpdateUserAttributesCommand`, unconditionally overwriting `custom:tenant_id`/`custom:role` on the *existing* Cognito identity — this is the exact unsafe cross-tenant-rebind fallback handoff §4.10 flags. It has no check for which tenant the existing identity currently belongs to.
- `app_users` seed (`INSERT ... ON CONFLICT (email, tenant_id) DO UPDATE`) happens in a `try/catch` that only logs on failure (`provision.js:198-200`) — **the route still returns `success: true`** even if this seed fails. This is exactly the false-success behaviour handoff §4.11 forbids repeating.
- No idempotency key anywhere in this route. A retried POST with the same logical intent creates a second tenant (new UUID, new slug collision only if the exact same slug was reused — a different slug, e.g. auto-suffixed by a caller's retry logic, would silently create a duplicate tenant for the same commission intent).

### 1.2 Suspend / Resume (`admin.js:236-254`)

```js
router.patch("/tenants/:id/suspend", async (req, res) => {
  await query("UPDATE tenants SET status = 'suspended', ... WHERE id = $1", [req.params.id]);
});
router.patch("/tenants/:id/reactivate", async (req, res) => {
  await query("UPDATE tenants SET status = 'active', ... WHERE id = $1", [req.params.id]);
});
```

- Auth: `requirePlatformKey` (router-level `.use`, line 19) — same non-operator-attributed auth as commission.
- No precondition check (no check that the tenant exists, is not already suspended, or was ever active/trial).
- **`reactivate` unconditionally sets `status = 'active'`** — confirmed the exact bug handoff §4.2 describes: a `trial` tenant suspended mid-trial and then reactivated becomes `active` (a live paying-tier status), not restored to `trial`. There is no captured "prior state" anywhere in this code path.
- No reason, no idempotency key, no ledger, no before/after evidence, no effective-state re-observation.

### 1.3 Access denial on suspend (`middleware/auth.js:258-278`, `checkDemoExpiry`)

```js
if (tenant.status === "suspended") {
  return res.status(403).json({ ... "Account suspended" });
}
if (tenant.trial_ends_at && new Date(tenant.trial_ends_at) < new Date()) {
  return res.status(403).json({ ... "Demo access expired..." });
}
next();
```

- Confirmed exactly what handoff §4.3 describes: this is a **block-list** (`suspended` is denied; everything else, including `cancelled`, passes through). There is no `decommission`/`cancel` runtime status today that this middleware treats as terminal.
- Fails open on a DB error (`catch { ... next(); }`, line 276) — an existing, unrelated design choice (availability over strict denial on infra failure). Noted as a real interaction with §4.3's certification requirement: the "next request is denied" proof must run against the healthy-DB path; a DB outage during that proof would fail open. This is pre-existing behavior, not something 1A.8 introduces or is asked to change.

### 1.4 `tenants.status` / `tenants.tenant_kind` constraints (confirmed via `001_tenants_foundation.sql:19`, `270_explicit_platform_tenant.sql:92-94`)

```sql

tenant_kind check (tenant_kind in ('customer', 'platform'))
```

Exactly as handoff §4.1/§4.15 state. `synthetic` is not a valid `tenant_kind` and must never be inserted.

### 1.5 A second, independent path already writes `tenants.status = 'cancelled'` (`migrations/006_billing_webhooks.sql:147-156`)

```sql
when 'subscription.cancelled' then
  update subscriptions set status = 'cancelled', ...
  update tenants set status = 'cancelled', ... where id = v_tenant_id;
```

The Razorpay billing-webhook handler already transitions a tenant to `status = 'cancelled'` as a **side effect of billing cancellation**, entirely outside any Governance/Management-API path. This is real, load-bearing prior art confirming `cancelled` is the correct terminal runtime status for decommission to converge on (handoff §4.1's mapping is validated by real usage, not invented) — but it also means **Governance's decommission command is not the only legitimate way a tenant reaches `cancelled`**. The canonical Infrakinetic decommission service (1A.8.2) must treat "already `cancelled`" as a valid starting precondition for a safe replay/no-op (§4 failure matrix: "decommission already-decommissioned tenant → safe replay/no duplicate destruction"), not assume Governance is the sole writer of that state. Governance must never directly mutate Finance/Billing subscription rows (non-negotiable invariant #7) — this confirms handoff §4.7's warning is grounded in a real, already-shipped code path, not a hypothetical.

### 1.6 Existing repo-boundary guard (`src/migration/legacyProvisioningSurfaceBaseline.js`)

## 3. Locked decisions for 1A.8 (ground-truthed, not merely restated from the handoff)

### 3.1 Two independent state facts — Governance lifecycle vs. Infrakinetic runtime status

Confirmed real: the master-plan §22 lifecycle (`draft → requested → approved → provisioning → active`, `active ⇄ suspended`, `active → decommission_requested → decommissioning → decommissioned`) has **no corresponding column anywhere in Infrakinetic**. The only real runtime fact is `tenants.status ∈ {trial, active, suspended, cancelled}` (§1.4 above). These must be persisted as two separate fields (Governance-side `commissioned_tenants.lifecycle_state` vs. `commissioned_tenants.last_observed_runtime_status`), never collapsed into one.

| Governance `lifecycle_state` | Required runtime `tenants.status` |
|---|---|
| `draft` / `requested` | no runtime tenant yet (no row) |
| `approved` | no runtime tenant yet (authorized to provision) |
| `provisioning` | owner operation executing (row may or may not exist yet, mid-flight) |
| `active` | `trial` **or** `active` (both are "the tenant is live") |
| `suspended` | `suspended` |
| `decommission_requested` / `decommissioning` | transitional (row still whatever it was; not yet `cancelled`) |
| `decommissioned` | `cancelled` |
| `failed` | unknown — never inferred absent; must be independently observed, not assumed |

### 3.2 Resume restores the *recorded* prior runtime status, never a fixed value

The existing 1A.6 `recoverEngineState()` pattern (`engineStateOperation.ts:308-346`) already solves this exact problem for engine state: it reads `priorState` out of the *original* operation's own `beforeStateSafeSnapshot`, never hardcodes a target. 1A.8.4's tenant-resume orchestration must follow the identical shape: the **suspend** operation's before-state snapshot must capture `{ runtimeStatus: 'trial' | 'active', trialEndsAt }` (read via the same `GET /management/v1/tenants/:identifier` route already live from 1A.7 — no new read primitive needed for this part), and **resume** must read that snapshot back and request exactly that status, never `'active'` unconditionally. This directly fixes the real bug confirmed in §1.2.

`commissioned_tenants.pre_suspend_runtime_status` (handoff §8's field list) is a *denormalized convenience copy* of the same fact for fast UI display — the ledger's own before-state snapshot on the suspend operation remains the source of truth a resume operation actually reads, the same way `recoverEngineState()` reads the ledger, not a side table, for the engine-state case. This keeps 1A.8 architecturally consistent with the one precedent this codebase already has for "restore the real prior state."

### 3.3 Decommission access denial requires an owner-side middleware change (real gap, real fix location identified)

Confirmed real gap (§1.3): `checkDemoExpiry` (`middleware/auth.js:267-269`) is a **block-list** (`suspended` only). Handoff §4.3's "prefer an allow-list" decision is adopted: this slice's scoping identifies the exact change 1A.8.2 must make —

```js
// current (block-list):
if (tenant.status === "suspended") { deny }

// required (allow-list):
if (tenant.status !== "active" && tenant.status !== "trial") { deny }
```

This is an Infrakinetic-side product-code change belonging to 1A.8.2 (canonical lifecycle service slice), not 1A.8.0. It is called out here because 1A.8's exit gate explicitly requires proving "cancelled tenant cannot make a normal tenant request" (handoff §4.3, §11 DECOMMISSION), and that proof is impossible until this one-line change ships. Recorded now so 1A.8.2 does not have to rediscover the exact line.

### 3.4 New scopes required (confirmed: do not exist today)

`backend/src/identity/roles.ts:19-60` currently defines `tenants.read`, `tenants.commission`, `tenants.suspend` — **`tenants.resume` and `tenants.decommission` do not exist**, confirmed by reading the full `SCOPES` array. 1A.8.1 must add both, and extend `provisioning_operator`'s `ROLE_SCOPE_CEILING` entry (currently `tenants.read, tenants.commission, tenants.suspend, engines.read, engines.entitlement.write, identity.read, audit.read`) to include them. `platform_admin`/`break_glass` already hold the full `SCOPES` array by construction (`ROLE_SCOPE_CEILING.platform_admin: SCOPES`), so they need no explicit change. Per handoff §4.4: `tenants.suspend` must never be overloaded to authorize decommission — each of the four commands keeps its own scope, matching the existing one-scope-per-mutation-shape discipline `engines.platform_state.write` already established.

### 3.5 Risk classification: R2 for all four commands

Reuses the exact policy table already in `riskClassification.ts` (`R2: requiresReason: true, requiresApprovalWorkflow: false`) — no schema or policy-table change needed, only a new `tenantRiskClassFor()` helper (mirroring `engineStateOperation.ts`'s `riskClassFor()`) that returns `"R2"` unconditionally for `tenant.commission`/`tenant.suspend`/`tenant.resume`/`tenant.decommission`. Matches handoff §4.5's reasoning (tenant-scoped, decommission ≠ hard delete, R2 already covers "suspension" per master-plan §20's own R2 example list) and requires no master-plan change to the risk-class definitions themselves — only the per-action mapping, which is implementation detail the master plan deliberately leaves to each phase (confirmed: §20 defines classes generically, never pins specific actions beyond illustrative examples).

### 3.6 `tenant_kind = 'platform'` guard applies here (locked in 1A.7, enforced starting now)

1A.7's own scoping doc (`docs/1A.7_scoping.md`, "Decisions — locked", #2) already named this requirement for "any future tenant-management mutation phase (1A.8 commissioning, suspend/decommission, etc.)." 1A.8.2's canonical suspend/resume/decommission service must fail closed (`403`/`409`, not silently no-op) if the target tenant's `tenant_kind === 'platform'` (the single reserved row at `00000000-0000-0000-0000-000000000001`), unless a future master-plan revision explicitly names an exception. Commission never produces `tenant_kind = 'platform'` (not accepted as request input at all — see §4.5).

### 3.7 Decommission ≠ delete, ≠ Billing cancellation-by-assumption

Confirmed by §1.5: `tenants.status = 'cancelled'` is already a real, independently-owned billing-webhook side effect. 1A.8.2's decommission service must:
- never `DROP`/`DELETE` any tenant-owned row (documents, Finance records, audit history, Cognito identity);
- treat "tenant already `cancelled`" (however it got there) as an idempotent-safe starting state, not an error;
- never write `subscriptions`/`razorpay_*` fields — those remain Finance/Billing-owned (non-negotiable invariant #7); Governance decommission mutates `tenants.status` only, through the same kind of scoped, single-purpose SQL the billing webhook itself uses, not a broader "cancel everything" transaction.

### 3.8 PII boundary — concrete implementation constraint, not just policy

`evidence.ts`'s `buildSafeSnapshot()`/`redactSecretShapedFields()` (confirmed by reading `SECRET_KEY_PATTERN`, line 20) redacts **secret-shaped** keys/values (`password`, `token`, `credential`, PEM blocks, JWT-shaped strings) — it has **no PII-awareness**. An email address does not match `SECRET_KEY_PATTERN` and would pass through `buildSafeSnapshot()` unredacted if a caller naively snapshotted `{ admin_email, admin_name }` as before/after evidence. **1A.8.4's commission orchestration must never pass `admin_email`/`admin_name` into `buildSafeSnapshot()` at all** — the ledger's before/after snapshots for `tenant.commission` must carry only `{ tenantId, slug, plan, accountType, lifecycleState }`-shaped data, matching handoff §4.12's "masked email if necessary; hash if useful; outcome/status; not unnecessary raw PII." This is a concrete code-review criterion for 1A.8.2/1A.8.4, not a restatement of policy.

Governance's `commissioned_tenants` control row (handoff §8's field list) likewise never stores `admin_email`/`admin_name` — that PII lives only transiently in the request and durably in Infrakinetic's own `tenant_pending_admins`/`app_users`/Cognito (the owning runtime systems), exactly as handoff §4.12 requires.

### 3.9 Owner-side idempotency is a real, currently-missing gap

Confirmed: `provision.js` has **no idempotency key handling anywhere** — a retried `POST /provision-tenant` (network ambiguity: client sent, server committed, response lost) creates a second tenant if the retry uses a different slug, or a `409` if it reuses the same slug (an accidental, not designed, protection). Governance's own `management_idempotency_keys`/`management_operations` (1A.5) only protects the *Governance→Infrakinetic call*, not the reverse case where Infrakinetic itself receives the call twice through two different Governance idempotency keys (e.g. Governance restarted between reservation and the HTTP call, or an operator's script bug). Per handoff §4.13, this requires a **new, Infrakinetic-owned** durable command-receipt table — distinct from, and never a duplicate of, Governance's own ledger. Proposed shape (locked for 1A.8.1 to implement as a migration):

```sql
create table tenant_lifecycle_commands (
  idempotency_key   text primary key,
  action            text not null,          -- 'tenant.commission' | 'tenant.suspend' | 'tenant.resume' | 'tenant.decommission'
  commission_request_id uuid,                -- stable across retries even before tenant_id is known (see §3.13)
  tenant_id         uuid,                    -- null until commission actually creates the row
  request_hash      text not null,
  correlation_id    uuid not null,
  operator_id       uuid not null,           -- from the verified management assertion, never request body
  status            text not null check (status in ('accepted','executing','completed','failed')),
  result            jsonb,                   -- safe result only, redacted the same way evidence.ts redacts
  created_at        timestamptz not null default now(),
  updated_at        timestamptz not null default now()
);
```

This is intentionally the mirror image of Governance's own `management_idempotency_keys`/`management_operations`, applied on the owner side — not a new architectural concept, just closing the one direction the existing 1A.5 design does not cover (§4.13's "Governance-side idempotency alone is therefore NOT sufficient").

### 3.10 Never re-bind an existing Cognito identity to a different tenant

Confirmed unsafe fallback exists today (§1.1, `provision.js:172-185`). 1A.8.2's canonical commission service must replace the `UsernameExistsException → AdminUpdateUserAttributesCommand` fallback with a three-way check against the *verified* existing identity's current `custom:tenant_id`:
- matches this same tenant → idempotent/reconciliation, proceed without re-creating;
- matches a different tenant → hard conflict (`409`, no attribute mutation, no silent reassignment);
- ambiguous (e.g. lookup itself fails, or the attribute is missing) → operator review, never a default action.

The existing pre-check (`provision.js:55-66`, querying `app_users`) only catches an identity that has *already completed* first-login reconciliation into some tenant's `app_users` — it does not catch a Cognito user created but never linked. The three-way check above must query Cognito directly (`AdminGetUserCommand`), not rely on the `app_users` pre-check alone.

### 3.11 Initial-admin failure is a real partial failure, not swallowed

Confirmed real gap (§1.1: `app_users` seed failure is logged and swallowed, route still returns `success: true`). When `send_invite = true`, 1A.8's commissioning orchestration (1A.8.4) must treat a downstream identity-provisioning failure (Cognito create/update failure, or `app_users` seed failure) as `partially_completed` or `failed`, never silently `completed`. Holiday-calendar seed failure remains `completed-with-warning` (already correct in real code — §1.1, no change needed there).

### 3.12 Synthetic tenant type

Confirmed: `tenant_kind` constraint is `('customer', 'platform')` only (§1.4). The 1A.8.6 certification tenant is `tenant_kind = 'customer'` with an obviously synthetic name/slug (e.g. `name: "Phase 1A.8 Synthetic Certification"`, `slug` prefixed `1a8-cert-`). `synthetic` is never inserted as a `tenant_kind` value anywhere.

### 3.13 Stable commission-request identity, independent of idempotency key retries

Per handoff §4.13's closing point: a `commission_request_id` (UUID, generated by Governance *before* the first owner call, distinct from `idempotency_key`) must be threaded through every retry/repair of the same commissioning intent, so that if the first attempt's response is lost, a human operator's *manual* repair action (a genuinely new idempotency key, per §4.14 "retry is not replay") can still be correlated back to the same intended tenant via `commission_request_id`, even before `tenant_id` is known. This is the field that makes `tenant_lifecycle_commands.commission_request_id` (§3.9) meaningful across a repair, not just a raw replay.

## 4. Request/response contracts (design only — not implemented this slice)

### 4.1 Commission — `POST /management/v1/tenants/commission` (Infrakinetic), fronted by `POST /management/tenants/commission` (Governance)

Request body (Governance → Infrakinetic, inside the signed-assertion-protected call):

```jsonc
{
  "name": "string, required",
  "slug": "string, optional — server-side slugify(name) if omitted",
  "plan": "string, required — validated against public.plans, same as today",
  "industry": "string, optional, default 'general'",
  "country": "string, optional, default 'IN'",
  "timezone": "string, optional, default 'Asia/Kolkata'",
  "accountType": "'demo' | 'live', required",
  "trialDays": "integer >= 0, optional — only meaningful when accountType='demo'; reject negative/absurd (e.g. >365) values, do not invent a new commercial policy",
  "initialAdmin": { "name": "string", "email": "string" },   // optional as a whole; required together if present
  "sendInvite": "boolean, default true",
  "reason": "string, required (R2 policy)",
  "commissionRequestId": "uuid, required — see §3.13",
  "idempotencyKey": "string, required",
  "commandId": "uuid, required"
}
```

Explicitly **absent**: `enabled_engines`, `enabled_integrations`, any AI/release/provider field (handoff §4.8, locked). `tenant_kind` is never accepted as input — always `customer` server-side.

Response mirrors the `PUT /engine-state/:engineKey` shape (canonical tenant, commandId, idempotencyKey, previousState: none (creation), resultingState, operatorId, correlationId, executedAt) plus `tenantId`, `slug`, `lifecycleOutcome` (`completed | partially_completed | failed`) and, when partial, which stage failed (`identity-provisioning | app-users-seed`, never `holiday-seed` since that's a warning not a failure per §3.11).

### 4.2 Suspend / Resume / Decommission — `POST /management/v1/tenants/:tenantId/{suspend|resume|decommission}`

Common request body: `{ reason: string, idempotencyKey: string, commandId: string }`. No other fields — these are pure state transitions, no payload beyond why.

Each route must (mirroring `engine-state/:engineKey`'s existing `MANAGEMENT_TARGET_ENGINE_MISMATCH` check at `routes/management/v1/index.js:164-171`) verify `req.managementContext.targetTenantId === req.params.tenantId`, rejecting with a new `MANAGEMENT_TARGET_TENANT_MISMATCH` (409/403) if the signed assertion was minted for a different tenant than the URL names — this is the tenant-scoped analogue of an already-proven pattern, not a new design.

Response: `{ tenantId, previousRuntimeStatus, requestedRuntimeStatus, resultingRuntimeStatus, operatorId, correlationId, executedAt }`.

### 4.3 Governance-side command families

Reuses the exact command-family names already listed in master plan §63 and already anticipated by `commandEnvelope.ts`'s generic `requested_action: string` field — no envelope shape change: `tenant.commission`, `tenant.suspend`, `tenant.resume`, `tenant.decommission`.

## 5. Owner-side idempotency design — summary

Already detailed in §3.9/§3.13. Key rule restated for clarity: **replay** (same `idempotencyKey`, same payload hash) returns the existing durable `tenant_lifecycle_commands` row's result with **zero** new side effects — no second `provision_tenant()` call, no second Cognito call. **Repair** (a human operator retrying after a confirmed partial failure) always uses a **new** `idempotencyKey`, carries `causationId` back to the original Governance-side operation, and carries the *same* `commissionRequestId` — the owner service inspects `tenant_lifecycle_commands` by `commission_request_id` to determine which stages already completed (e.g. tenant row exists, Cognito user does not) and performs only the remaining stage(s), never re-running `provision_tenant()` against an existing tenant.

## 6. Partial-failure matrix (locked, per handoff §14 — reproduced with implementation notes)

| Scenario | Outcome |
|---|---|
| Governance DB unavailable before submit | No owner mutation. Governance-side `DatabaseUnavailableError` (already an existing type, `db/errors.js`) surfaces before any assertion is minted. |
| Management assertion mint fails | No owner mutation — minting happens before any network call in the existing `engineStateOperation.ts` pattern; the tenant-lifecycle orchestration follows the same order. |
| Network fails before owner receives command | `failed` with `partialFailureState.stage: "mutation-call"` (existing pattern, `engineStateOperation.ts:217-226`). Operator must reconcile (check `GET /management/v1/tenants/:id`) before any retry, per master-plan §59 "timeout does not justify blindly creating a new command." |
| Network fails after owner accepts command | Owner's `tenant_lifecycle_commands` row (§3.9) resolves the ambiguity on the next call with the same idempotency key — replay returns the durable result; no duplicate tenant. |
| `provision_tenant()` fails before commit | `failed`; no tenant row exists (the function raises inside the same transaction as the insert — already atomic in real code). |
| Tenant DB commits, Cognito fails | `partially_completed` (§3.11) — tenant exists, `sendInvite` was requested but no identity was created. |
| Cognito succeeds, `app_users` seed fails | `partially_completed` when `sendInvite=true` (§3.11 — this exact case is currently swallowed in real code and must not be after 1A.8.2). |
| Holiday-calendar seed fails | `completed-with-warning` — unchanged from real, already-correct behaviour (§1.1). |
| Fresh effective read fails after mutation | `partially_completed` (existing pattern, `engineStateOperation.ts:252-262`). |
| Fresh effective state mismatches desired | `partially_completed` (existing pattern, `engineStateOperation.ts:264-275`). |
| Duplicate slug | `409` conflict at the owner call, mapped to `failed` on the ledger — no second tenant (existing `provision_tenant()` behaviour, reused as-is). |
| Admin email belongs to another tenant | `409` conflict — never rebind (§3.10, new check replacing the unsafe fallback). |
| Same idempotency key + changed payload | Reject — existing `IdempotencyConflictError` (`managementOperationLedger.ts:368-370`), reused as-is; owner side gets the equivalent `tenant_lifecycle_commands.request_hash` check. |
| Suspend an already-suspended tenant | **Locked decision**: idempotent no-op (owner service checks current status first; if already `suspended`, returns success without a second mutation) — matches the general "replay is safe" philosophy rather than inventing a new conflict class for a state that is not actually wrong. |
| Resume a non-suspended tenant | **Locked decision**: state conflict (`409`) — resume is only meaningful from `suspended`; silently no-op-ing here would risk masking an operator mistake (e.g. double-clicking Resume after it already succeeded is the no-op case above; calling Resume on a tenant that was never suspended is a genuine mistake worth surfacing). |
| Decommission an already-decommissioned tenant | Safe replay/no-op (§3.7 — matches the real "cancelled via billing" interaction). |

## 10. Exact tests (mapped onto real file conventions, per handoff §15)

Following the existing conventions already established (`routes/management/v1/__tests__/index.test.js` for Infrakinetic route tests, `backend/src/management/operations/__tests__/engineStateOperation.test.js`-equivalent shape for Governance orchestration, `backend/src/routes/management/__tests__/` for the Governance HTTP layer):

**State machine** — valid/invalid `lifecycle_state` transitions (new `tenantLifecycle.ts` state table, mirroring `lifecycle.ts`'s `isValidTransition`), no terminal resurrection (`decommissioned` has no outgoing edges, matching `lifecycle.ts`'s own `completed`/`failed` pattern).

**Authorization** — `platform_viewer` (no `tenants.commission`) denied commission; `provisioning_operator` (once granted §3.4's new scopes) allowed all four; an operator missing exactly one of the four scopes denied exactly that one action; tenant-population JWT rejected (already covered generically by `requireManagementApiAuth`'s existing test suite — new tests only need the tenant-specific routes added to that suite's route list).

**Idempotency** — same key/same payload → replay, zero owner-side mutations (assert via a call-count spy on `provision_tenant`); same key/different payload → reject at both Governance ledger and owner receipt layers; ambiguous-transport case (mint succeeds, HTTP call throws) → `failed`, and a same-key retry after that failure is a legitimate new attempt (owner side sees no prior `completed`/`accepted` receipt) — this "failed is not terminal for the idempotency key" nuance must be tested explicitly since it differs from `completed`.

**Tenant isolation** — assertion minted for tenant A used against `:tenantId` = tenant B → `MANAGEMENT_TARGET_TENANT_MISMATCH`; commission producing a tenant later suspended by an assertion targeting a *different* tenant's id → rejected.

**Commission** — full success with `sendInvite=true`; `sendInvite=false` (two-step); invalid plan (owner `provision_tenant()` raises, mapped to `400`); slug collision (`409`); existing-identity-same-tenant (idempotent path); existing-identity-different-tenant (`409`, no attribute mutation — assert via a Cognito client spy that `AdminUpdateUserAttributesCommand` was never called); Cognito failure with tenant already created → `partially_completed`; `app_users` seed failure → `partially_completed`.

**Suspend** — effective `tenants.status` becomes `suspended`; before-state snapshot captures real prior `trial`/`active` + `trial_ends_at`; suspending an already-suspended tenant is a no-op replay (§6); suspending the reserved `platform` tenant → `403`/`409` (§3.6).

**Resume** — a `trial`-suspended tenant resumes to `trial` (not `active`) with `trial_ends_at` intact; an `active`-suspended tenant resumes to `active`; resuming a non-suspended tenant → conflict (§6).

**Decommission** — no `DELETE`/`DROP` anywhere (grep the implementation, same technique `1A.5`'s own status doc used for secret-shaped values); effective `cancelled`; **next tenant-scoped request denied** — an integration test hitting a real tenant-scoped route (or the `checkDemoExpiry` unit directly) after decommission, proving §3.3's allow-list fix; decommissioning an already-`cancelled` (e.g. billing-cancelled) tenant → safe replay, no error.

**Evidence** — no password/token/secret in any ledger row (existing `evidence.ts` guarantee, re-asserted for the four new action types); no raw `admin_email`/`admin_name` in any before/after snapshot (§3.8 — new assertion, since `evidence.ts` alone does not guarantee this).

**UI** — no raw command envelope/internal route/SQL/Cognito-sub shown as primary UX; lifecycle action buttons match `{status, scopes}` exactly per §8's table; operation `partially_completed`/`failed` states rendered distinctly from `completed` (not collapsed to a generic "done"); responsive at desktop/narrow-desktop/mobile widths (matches this repo's existing browser-verification practice for frontend changes).
