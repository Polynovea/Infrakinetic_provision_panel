## 2026-09-14 — plan owner declines the tenant-pool-reuse deviation; dedicated pool restored

The "Recommendation" below (reuse Infrakinetic's existing Cognito pool via a new, dedicated app client) was explicitly
recorded as "a deviation from §15's literal text that only the plan owner can ratify... not silently substituted."
It was never ratified. The plan owner has now explicitly declined it. **The canonical, locked decision is the
master plan's original §15 text: a separate, dedicated `polynovea-platform-operators` Cognito user pool**, with
mandatory MFA and a separate Governance authentication audience, a dedicated app client/domain, Authorization Code +
PKCE, and the callback handled by the Governance backend only — no Cognito token or client secret ever reaches the
browser. Do not reuse the tenant/customer Cognito pool for operator identity, via another app client or otherwise.

The "Open question" below (pool-wide MFA posture of the *existing* pool) is now moot for this decision — a dedicated
pool's MFA policy is set directly at creation, not inferred from Infrakinetic's tenant-pool configuration. The
provisioning list in "AWS resources required to finish live 1A.2" below (dedicated pool, one app client, break-glass
identities, environment values, one real operator record) remains the correct list and is unaffected by this
reversal — it was written against the dedicated-pool design in the first place.

The analysis below (topology evidence from `CRM/api-server`, why a new app client on the existing pool would have
satisfied the same security invariants) is left intact as the evidence trail that led to a recommendation the plan
owner was entitled to reject, not as a claim it was ever adopted.

## 2026-09-11 follow-up — corrected identity topology, bootstrap mechanism

The original version of this document below (first-pass 1A.2, same day)
assumed a **new**, dedicated `polynovea-platform-operators` Cognito pool was
required, per the master plan's §15 literal text. That assumption was
challenged and re-investigated. Findings:

### Existing Cognito/auth architecture (read from source, `CRM/api-server`)

- **One Cognito user pool, one app client**, already live in production
  (region `ap-south-1`; exact pool/client IDs deliberately not repeated in
  this document — see "no secrets in docs" below). Configured via
  `COGNITO_REGION` / `COGNITO_USER_POOL_ID` / `COGNITO_CLIENT_ID` in
  `api-server/.env`, constructed in `api-server/src/lib/cognito.js` and
  `api-server/src/lib/cognitoJwt.js`.
- **Every user in that pool is structurally tenant-bound.** ID tokens carry
  `custom:tenant_id` and `custom:role` custom attributes
  (`api-server/src/middleware/auth.js`). The role vocabulary
  (`ROLE_LEVELS`: `master_admin, admin, manager, member, prospect, viewer,
  employee, client`) is a **tenant-scoped** ladder — `master_admin` there
  means "highest role *within one tenant*," not cross-tenant platform
  authority. There is no concept of a platform-wide operator role anywhere
  in this pool's current usage.
- **The backend never trusts the token's role claim as final authority.**
  `requireActiveAccount` (same file) re-derives `req.role` from the live
  `app_users.role_key` on every request and 401s if the underlying row's
  `status` isn't `'active'` — Cognito claims are a starting point, the
  database row is authoritative. This is the *same pattern* 1A.2's
  `requireManagementApiAuth` already uses (Cognito proves identity;
  `OperatorDirectory` decides privilege) — independently arrived at, now
  confirmed consistent with this codebase's existing security doctrine
  elsewhere, not a novel idea.
- **`public.platform_tenant_id()`** (`api-server/src/lib/platformTenant.js`)
  is a fixed sentinel UUID (`00000000-...-000000000001`) used throughout the
  schema for **RLS/content ownership** of platform-shared *data* (default
  document templates, routing rules, workflow definitions, ML calibration
  data). It is **not** the real internal Polynovea operating tenant — it is
  a synthetic ownership marker, not a tenant with real employee users.
- **A real, separate "internal Polynovea tenant" is already a named concept**
  in this codebase, distinct from the sentinel above —
  `api-server/src/release/releaseStage.js`'s CANARY gate explicitly excludes
  "the internal Polynovea tenant" from ever being used as a canary, "per
  Phase-1A deferral." This confirms the master plan's own **§64 "1A.18 —
  Internal Polynovea tenant"** is where real commissioning is sequenced:
  *"Commission the real internal tenant through the exact same pipeline used
  for customers. No special DB shortcut."* — i.e. through Phase 1A's own
  governed tenant-commissioning workflow (1A.7 tenant registry → 1A.8
  commissioning lifecycle), which does not exist yet at 1A.2.
- **The existing (legacy, pre-remediation) tenant+admin provisioning
  mechanism** is `api-server/src/routes/provision.js`'s `POST
  /provision-tenant` (protected by `requirePlatformKey`, a single shared
  secret — explicitly *not* usable as Phase 1A auth per master-plan §5).
  It: (1) calls SQL function `provision_tenant()` to create a `tenants` row
  (raises if the slug already exists — not idempotent on its own), (2)
  calls Cognito `AdminCreateUserCommand` with `custom:tenant_id` +
  `custom:role: "master_admin"`, (3) seeds an `app_users` row. This is the
  literal mechanism `legacyProvisioningSurfaceBaseline.js` says "Polynovea
  itself and every real tenant have been provisioned through" historically —
  i.e. whatever internal Polynovea tenant already exists (if one does) was
  most likely created this way, informally, before this remediation
  programme existed. **This session has no database access to confirm
  whether it already exists** (see "Exact technical restriction" below).

### Does the master plan require a *physically* separate pool?

§15's literal text says "Dedicated Cognito pool:
`polynovea-platform-operators`." Read strictly, yes. But the evidence above
shows the *security-relevant* requirements the plan is actually protecting —
README hard rule #5 ("no tenant identity accepted as platform operator"),
§5 ("must never reuse `requirePlatformKey`"), §69 invariant #1 ("tenant user
is not platform operator") — are about **authority never being tenant-derived**,
not about physical pool count. 1A.2's `CognitoIdentityProvider` already
never reads role/tenant/privilege claims from the token at all (see "Why
authorization is not derived from the Cognito token" below) — the entire
authority decision lives in `OperatorDirectory`, keyed by `sub`. A Cognito
token minted by the *existing* pool, under a **new, dedicated app client**
scoped only to this backend, satisfies every one of those invariants:
Cognito still only proves "this is a real, authenticated human" (via the
existing, already-hardened, already-MFA-capable infrastructure); it asserts
nothing about tenant membership or role that this backend would ever trust;
and a tenant user's token is rejected at the audience-verification step
before `OperatorDirectory` is even consulted (proven in
`cognitoIdentityProvider.test.ts`), exactly as it would be against a
separate pool.

**Recommendation (evidence-based, not yet AWS-executed): reuse the existing
pool with a new, dedicated app client**, rather than a second pool. This is
a **deviation from §15's literal text** that only the plan owner can ratify
— recorded here as a decision for you to confirm or override, not
silently substituted. If ratified, the master plan text should be amended
to reflect it rather than left contradicting the built system.

**Open question this session cannot resolve without AWS access:** whether
the existing pool's *pool-wide* settings (password policy, MFA
enforcement mode) already meet "MFA mandatory" for every user, since
Cognito enforces MFA mode at the pool level, not per app client. If the
existing pool's MFA is `OPTIONAL` pool-wide, a new app client alone cannot
force MFA for just the operator population — that would need either
pool-wide MFA tightening (risk: affects every existing tenant user) or a
Cognito group + custom auth-flow Lambda enforcing step-up specifically for
operator-app-client sign-ins. This must be checked against the live pool
config before the app-client approach is finalized as "safe as-is."

### Exact technical restriction on live provisioning (not a policy stance — a capability gap)

Checked, this session, before attempting anything:

- `aws sts get-caller-identity` → `Unable to locate credentials`. No AWS
  credentials of any kind (no CLI profile, no `AWS_ACCESS_KEY_ID`/
  `AWS_SECRET_ACCESS_KEY` in `api-server/.env`, no instance role — this
  session is not running on the production EC2 host). **This session
  cannot call any Cognito API, read or write, right now.** Production's own
  `cognito.js` relies on the AWS SDK default credential chain (an EC2
  instance IAM role at deploy time) — a mechanism this local session does
  not have.
- `api-server/.env`'s `DB_HOST=127.0.0.1:5433` (with `NODE_ENV=production`
  and real `polynovea.in`/`saas.polynovea.in` origins alongside it — this is
  the real production config file, present locally) — but port 5433 has
  **no active listener** in this session (`netstat`/raw TCP connect both
  confirm connection refused). Whatever tunnel normally forwards this to
  the real RDS instance is not currently open here. **This session cannot
  reach the production database either**, independent of any policy
  question.

Both blockers are informational/capability facts, not judgment calls: there
is currently no way, from this session, to create a Cognito user, query
whether a Polynovea tenant already exists, or write one. Establishing either
(opening a DB tunnel, obtaining AWS credentials) is itself a consequential
action on production access that this session did not take unilaterally —
flagged rather than attempted.

Separately from the capability gap: **creating a Cognito user account is
something this assistant does not execute directly even when credentials
are available and even when explicitly requested** — account creation
(including identity-provider accounts) is a hard operating boundary, not a
judgment call made per-request. This does not block the bootstrap design
below; it means the one Cognito-side step (`AdminCreateUser` for
`subrojitroy@polynovea.in`, or confirming one already exists) is the one
step a credentialed human performs, same as this document's original AWS
resource list already said before this correction.

### Bootstrap mechanism (built, locally tested; not yet run against anything real)

Per "prefer an existing canonical mechanism; if none exists, build a narrow
one" — no existing mechanism does the governance-side half of this (the
existing `provision.js` only knows about Infrakinetic tenant roles, not
Governance operator roles/scopes). Built:
**`backend/scripts/bootstrapOperator.ts`** (`npm run bootstrap:operator --
...`), operating on the 1A.2 interim operator store
(`backend/config/operators.seed.json`, renamed/repurposed from the old
`backend/fixtures/operators.fixture.json` — that file is deleted; nothing
else referenced it, the automated test suite builds its own operator
records independently, so this is zero-risk to `npm test`).

Properties (all locally verified — see table below):

- **Explicit, operator-invoked CLI only** — no HTTP surface, so it cannot
  become a general-purpose admin API by accident.
- **Idempotent** — re-running the exact same bootstrap is a safe no-op.
- **Refuses duplicate platform roots** — `--bootstrap-root` (for standing up
  the very first operator) refuses if the seed store already holds a
  *different* operator; re-asserting the same one is allowed through as the
  idempotent no-op case above.
- **Fails closed on ambiguous state** — an existing record for the same
  `cognito_sub` with *different* attributes is refused, not silently
  overwritten; a duplicate email bound to a different `cognito_sub` is
  refused.
- **Emits audit evidence** — every outcome (created / no_change / refused)
  appends a line to `backend/config/operator_bootstrap_audit.jsonl`
  (actor, reason, timestamp, result — no secrets, just identifiers and
  free-text justification).
- **Never handles a password/secret** — it takes a Cognito `sub` as input
  (produced separately, by whoever creates or already owns that Cognito
  identity); it has no code path that could see, store, or log a password,
  token, or MFA secret.
- **Does not encode the bootstrap operator's identity by email** — the
  script assigns whatever `--role` is passed; nothing in `requireManagementApiAuth`,
  `authorize.ts`, or the operator directory ever branches on an email string.
  Durable authority is the `OperatorRecord`'s `roles`/`scopes` fields, full
  stop — exactly the "do not implement `if email == ... => superadmin`"
  requirement.
- **Marked bootstrap-only** — its own header comment says so, and names
  which later subphases (1A.3 DB, 1A.5 ledger, 1A.18 tenant commissioning)
  should retire it.

Local behavioral test (synthetic `test-sub-*` identifiers only, run against
throwaway `--seed-path`/`--audit-path`, never touching the real
`config/operators.seed.json`, which remains `[]` in this commit): root
bootstrap succeeds; identical re-run is a no-op; a second `--bootstrap-root`
for a *different* subject is refused; a conflicting re-bootstrap of the
*same* subject with a different role is refused; a duplicate email under a
different subject is refused; `--dry-run` computes and prints without
writing; `--list` reflects true state. All nine scenarios behaved exactly
as designed.

### How the operator is "linked" to the internal tenant

Deliberately **not** a database foreign key — a literal FK from Governance's
(future) DB to Infrakinetic's `tenants`/`app_users` tables would itself be
the "no direct cross-database mutation" / "no shared DB credentials"
violation the whole repository boundary exists to prevent. The link is by
**shared identity**: the same human's Cognito `sub` (and email) can
independently be (a) a normal Infrakinetic tenant user of the internal
Polynovea tenant, with whatever `app_users.role_key` that tenant's own
Tenant Governance assigns, completely unrelated to (b) a Governance
`OperatorRecord` for that same `sub`, with whatever `roles`/`scopes`
Governance's own RBAC assigns. Holding (a) grants zero platform authority
under (b) unless a `OperatorRecord` is explicitly bootstrapped for that
`sub` — this is precisely "no customer identity can obtain equivalent
authority merely through Cognito membership or tenant association," proven
structurally (`OperatorRecord` has no `tenantId` field, and
`requireManagementApiAuth` never reads `custom:tenant_id` or
`custom:role`), not just by policy.

# Original 1A.2 status (first pass, same day, left intact — see follow-up above)

## Scope decision made this subphase

The master plan's `requireManagementApiAuth` / `/management/v1/*` language
(§6, §16, §64 "1A.4") is written primarily about the surface **Infrakinetic's
api-server** must eventually expose to accept commands from this backend.
That surface requires cross-repo, cross-team authorization this session does
not have, and 1A.4 is explicitly sequenced after this subphase.

1A.2, as scoped here, builds `requireManagementApiAuth` as **this backend's
own** operator-authentication boundary — the middleware that will protect
`polynovea-platform-governance`'s management API from its own frontend. This
is squarely inside the Governance repo, requires no Infrakinetic/CRM change,
and matches every other 1A.2 exit criterion (operator authenticates; tenant
identity is rejected; MFA-backed Cognito pool; roles/scopes; session
model; logout/revocation; step-up skeleton). The Infrakinetic-side
management surface remains 1A.4's deliverable, unstarted, in the other repo.

**If this reading is wrong** — if `requireManagementApiAuth` was meant as
the Infrakinetic-side surface after all — the code below is still not
wasted: the identity/session/audit model is IdP-agnostic and Infrakinetic's
future middleware would consume the same claim shape from a management
assertion this backend mints, using the same role/scope catalog.

## Why authorization is not derived from the Cognito token

Cognito (once provisioned) proves *authentication*: "this bearer holds a
valid, MFA'd session for subject X in the polynovea-platform-operators
pool." It is never asked to carry roles/scopes/status as claims. Those are
resolved, after token verification, from a governance-owned `OperatorRecord`
keyed by the token's `sub` — so revoking an operator, disabling one, or
changing their scopes takes effect immediately without waiting on a Cognito
token to expire or reconfiguring a pre-token-generation Lambda. See
`backend/src/identity/types.ts` and
`backend/src/middleware/requireManagementApiAuth.ts`.

## Built, local only

- **Role/scope catalog** (`backend/src/identity/roles.ts`) — the exact 8
  roles and 31 scopes from master plan §15, plus an authored
  `ROLE_SCOPE_CEILING` default RBAC matrix (the plan lists roles and scopes
  but does not pin a mapping; this is this subphase's own architecture
  decision, recorded so it can be revisited).
- **Operator/session/context types** (`backend/src/identity/types.ts`).
- **Typed rejection reasons** (`backend/src/identity/errors.ts`) — one class
  per negative case the spec requires (malformed / expired / bad signature /
  wrong issuer / wrong audience / operator not provisioned / disabled or
  revoked operator / revoked session / insufficient privilege / missing
  role / missing scope / step-up required / misconfigured).
- **Clean IdP abstraction** (`backend/src/identity/identityProvider.ts` +
  `backend/src/identity/providers/cognitoIdentityProvider.ts`) — only the
  Cognito file knows AWS exists; it verifies signature/issuer/audience/expiry
  via `jose` and JWKS, and returns nothing about privilege. Region/pool
  id/app client id/issuer/JWKS URI are environment-only
  (`backend/src/identity/cognitoConfig.ts`) — no hardcoded AWS account id,
  ARN, pool id, domain or secret anywhere in source. Config is loaded lazily
  (`backend/src/identity/providers/lazyIdentityProvider.ts`) so server boot
  and `/healthz` never require Cognito to exist — only an actual
  `/management/v1/*` request does, and it fails closed with
  `IDENTITY_PROVIDER_MISCONFIGURED` (500) rather than crashing the process.
  Verified live: booted the built server with zero `GOVERNANCE_COGNITO_*`
  vars set — `/healthz` returned 200, an unauthenticated management request
  returned 401 `TOKEN_MISSING`, and a bearer-token request returned 500
  `IDENTITY_PROVIDER_MISCONFIGURED` naming the missing variable.
- **`requireManagementApiAuth`** (`backend/src/middleware/requireManagementApiAuth.ts`)
  — authentication only: extracts the bearer token, verifies it via the
  IdentityProvider, resolves the operator record by Cognito `sub`, rejects
  unprovisioned/disabled/revoked operators and revoked sessions, cross-checks
  the operator's granted scopes never exceed its roles' permitted ceiling
  (defense in depth against a directory data-integrity bug), and attaches
  `req.operatorContext`. Every failure path is audited and returns a typed
  `{error, message, correlationId}` body; there is no default-allow branch.
- **`authorize.ts`** (`backend/src/middleware/authorize.ts`) — authorization,
  in a separate module on purpose (§69 invariant: authn/authz stay
  explicit and separate): `requireRole`, `requireScope`, and a
  `requireStepUp` **skeleton** (checks freshness of a step-up marker; does
  not perform a real MFA re-challenge — that needs live Cognito
  adaptive/step-up configuration).
- **Governance-owned persistence ports** (`operatorDirectory.ts`,
  `sessionStore.ts`, `auditSink.ts`) with in-memory 1A.2 adapters
  (`identity/adapters/`) and a fixture operator seed
  (`backend/fixtures/operators.fixture.json`). These are an explicit,
  documented interim: **without the 1A.3 database, operator
  provisioning/disablement requires editing the fixture file and
  redeploying** — not acceptable for real production operator management,
  but the correct shape for 1A.2 given the DB is deliberately a separate,
  later subphase. The adapter seam is designed so 1A.3 swaps in
  Postgres-backed implementations without touching the middleware, routes,
  or any test above the adapter layer.
- **Persistence schema** (`backend/migrations/0001_operator_identity_schema.sql`)
  — `operators`, `operator_roles`, `operator_scopes`, `operator_sessions`,
  `operator_auth_audit_log`. Authored to the exact shape the in-memory
  adapters already implement. **Not applied anywhere** — there is no
  Governance database (1A.3). Verified locally against an in-memory
  Postgres engine (`pg-mem`, no network, no RDS) in
  `backend/test/migrations/0001_operator_identity_schema.test.ts`: applies
  cleanly, creates all five tables, enforces the status/role/scope
  vocabulary via `CHECK`, enforces `cognito_sub` uniqueness, enforces the
  disabled-operator/`disabled_at` consistency constraint, and cascades
  operator deletion into roles/scopes/sessions.
- **Route integration points** (`backend/src/routes/management/index.ts`,
  mounted at `/management/v1` in `backend/src/index.ts`) — `GET /whoami`,
  `POST /session/logout` (revokes the caller's own session — proves
  logout/revocation end-to-end), `POST /session/step-up` (skeleton marker),
  `GET /audit/self-test` (requires `audit.read` scope), and
  `GET /audit/self-test/step-up` (requires fresh step-up + `platform_admin`
  role). These are **not** the 1A.4 read-contract surface
  (`/catalog`, `/tenants`, ...) — they exist only to prove the auth boundary
  is correctly wired into a real Express router, with structural
  deny-by-default (every route under the router either requires the base
  auth middleware plus an explicit role/scope, or is one of the two
  session-lifecycle routes any authenticated operator may call on
  themselves; there is no bare/unrestricted route).
- **Audit/provenance hooks** (`backend/src/identity/auditSink.ts`) — every
  auth success, auth failure, authz denial, session revocation, and step-up
  recording calls `AuditSink.record()`. 1A.2 ships a structured-console
  implementation (`ConsoleAuditSink`) and an in-memory one for tests
  (`InMemoryAuditSink`); this is **not** the immutable operator action
  ledger from master plan §19 — that is 1A.5's deliverable, and this sink's
  event shape is the seam 1A.5 replaces.
- **Architecture/import-boundary check**
  (`backend/scripts/check_no_infrakinetic_imports.mjs`, wired into
  `npm run check:no-infrakinetic-imports` and CI) — fails the build on any
  import specifier under `backend/src` that resolves outside `backend/src`
  or names the Infrakinetic/CRM tree. Automates what 1A.1 only proved by
  grep-by-hand.
- Dependency vulnerability check (`npm audit`): fixed a moderate `qs` DoS
  advisory reachable through `express` via a `package.json` `overrides`
  pin (`qs@^6.16.0`). Five `vitest`/`vite`/`esbuild` advisories remain —
  all dev-server-only (arbitrary file read / SSRF against a locally-run
  `vitest` watch process), not present in the built `dist/` output or any
  deployed path; fixing them requires a `vitest` v5 major bump, deferred as
  an accepted residual risk rather than done opportunistically mid-1A.2.

## Deliberately not done

- **The dedicated `polynovea-platform-operators` Cognito user pool does not
  exist.** No pool, no app client, no MFA policy, no groups — AWS
  provisioning is out of scope for this session per explicit instruction.
- **No real Cognito JWT was ever verified.** All negative/positive test
  coverage uses a locally generated RSA keypair and `jose`'s
  `createLocalJWKSet` — the exact same verification code path
  (`CognitoIdentityProvider`), a locally issued token instead of the network
  fetch to a real Cognito JWKS endpoint.
- **No real step-up/adaptive MFA challenge.** `requireStepUp` and
  `POST /session/step-up` are a skeleton per the 1A.2 exit criterion
  ("step-up skeleton"); they check freshness of a marker, not a real
  re-challenge. Do not route an R3+ action (§20) behind only this check.
- **No Governance database, no applied migration.** 1A.3.
- **No maker-checker, no break-glass hardware-MFA enforcement.** Later
  subphases/1A.19 per the master plan's own sequencing — `break_glass` exists
  in the role catalog only as a defined role/scope ceiling today.
- **No Infrakinetic-side `/management/v1/*` middleware.** See "Scope
  decision" above — that is 1A.4, in the other repository, and touching it
  now would violate the governance-plane boundary ("management-plane logic
  belongs in governance, not inside Infrakinetic" plus "no hidden coupling
  to CRM internals").
