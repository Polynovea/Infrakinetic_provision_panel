## Ground-truthing the real `tenants` table (instruction-equivalent of 1A.6's "ground-truth the existing primitive" step)

Read directly, not assumed from the plan:

- **Table**: `public.tenants` (`api-server/migrations/001_tenants_foundation.sql:12-40`), plus later additive `ALTER TABLE` columns across `062`, `082`, `131`, `239`, `270`, `276`.
- **Full real column set**: `id` (uuid pk), `name`, `slug` (unique), `plan` (`starter`/`growth`/`enterprise`/`performance_lab`), `status` (`active`/`suspended`/`cancelled`/`trial`), `trial_ends_at`, `industry`, `country` (default `'IN'`), `timezone`, `brand_name`, `brand_logo_url`, `brand_primary_color`, `brand_accent_color`, `support_email`, `seat_limit`, `storage_limit_mb`, `razorpay_customer_id`, `razorpay_subscription_id`, `next_billing_date`, `created_at`, `updated_at`, `tenant_kind` (`customer`/`platform`, migration `270`), `employee_code_prefix`, `attendance_import_token`, `governance_model`, `ceo_leave_threshold_days`, `product_learning_opt_in`/`_opt_out`/`_consent_version`/`_consented_at`.
- **No column exists** for: environment, data-residency (beyond `country`), release channel, support tier, or responsible operator. §21 names all five — they are not fabricable from real data today, so this phase cannot and will not invent placeholder values for them. Deferred, honestly, not glossed over.
- **`tenant_kind`** is the real customer/platform distinction (not an `is_internal` flag, which does not exist). Exactly one `platform`-kind row exists: the reserved, trigger-protected Platform Tenant (`00000000-0000-0000-0000-000000000001`, `migrations/270_explicit_platform_tenant.sql`).
- **No reusable read primitive exists.** Unlike 1A.6 (which reused `getPlatformEngineState()`/`setPlatformEngineState()` verbatim), there is no `listTenants()`/`getTenants()` function anywhere in the codebase. Every existing tenant listing is inline SQL: `api-server/src/routes/admin.js:31-55` (`GET /admin/tenants`, uses the RLS-bypass pool, and its SELECT includes `admin_email`/`admin_name` — real person PII, not something a management-API registry should re-expose) and `:58-85` (`GET /admin/tenants/:id`, same pattern). `api-server/src/routes/tenants.js:9-26` is single-tenant self-service (RLS-scoped, not a registry). Two `migrationLearning.js`/`tenantCalibrationModel.js` functions are single-tenant migration-calibration reads, unrelated to a registry.
- **This is a real, worth-flagging deviation from the 1A.5/1A.6 precedent**: this phase cannot be "wire together existing functions, invent nothing new" the way 1A.6 was. A new, sanitized read primitive has to be written. That is still the *right* shape of new code (a safe read model is exactly what §21/§61 ask for, and none exists), just not zero-new-code the way 1A.6's engine-state route was.

## Scope/action reuse

`tenants.read` already exists, unused, in the locked 1A.2 scope catalog (`backend/src/identity/roles.ts:20`), granted to `platform_viewer`, `platform_operator`, and `provisioning_operator` in `ROLE_SCOPE_CEILING`. No new scope needed — same reuse discipline as 1A.6's `engines.platform_state.write`. Proposed per-route `requested_action` values, matching the `engines.catalog.read` / `engines.state.read` split already established by `requireManagementScope`: `tenants.registry.read` (list) and `tenants.registry.detail.read` (single tenant).

## Proposed vertical, end to end (mirrors 1A.6's read-half exactly; no mutation, no ledger)

```
authenticated operator (Governance's own /management/tenants, human-facing)
  -> requireScope("tenants.read") [1A.2 authz, reused]
  -> listTenantRegistry() [new, Governance — read-only, no ledger entry: R0 per 1A.5's own
       risk-classification framework, which reserves the ledger for mutations/idempotency,
       not reads]
       -> mint one single-use assertion (scope tenants.read, action tenants.registry.read)
       -> GET /management/v1/tenants   (real, new Infrakinetic route)          [real, live]
  <- sanitized tenant list + observedAt (master plan §61 freshness envelope)
```

No `management_operations` ledger row is created for these reads, matching 1A.5's own design ("R0 = read-only, no reason required") and the fact that 1A.6's own read-only resolve/verify steps inside `requestEngineStateChange()` likewise never create a ledger entry by themselves — only the mutation in between does. Authn/authz denial is still audited via the existing `deps.auditSink` perimeter (`authz.denied` events), same as every other route.

**Freshness (§61), concretely for this phase**: no caching layer exists or is being built here — every call is a live query. "Freshness explicit" is satisfied by stamping every response with `observedAt: <read timestamp>` rather than letting a caller assume the data could be cached; there is no lag/staleness state machine to build yet (that's 1A.10's reconciliation phase, which deals with *desired vs. effective* drift, not registry currency).

## Decisions — locked 2026-09-14

1. **Sanitized field list — locked**: `id, name, slug, tenant_kind, plan, status, trial_ends_at, industry, country, timezone, seat_limit, storage_limit_mb, created_at, updated_at`. Explicitly excluded, and treated as an **architectural boundary, not a temporary sanitization pass**: `admin_email`/`admin_name` (person PII), `razorpay_customer_id`/`razorpay_subscription_id`/`next_billing_date` (financial-provider state — billing/FinOps visibility belongs in a later, dedicated billing projection/read model joined on `tenant_id`, not an expansion of this core registry contract), `employee_code_prefix`/`attendance_import_token` (payroll-internal, secret-shaped), `governance_model`/`ceo_leave_threshold_days`, `brand_*`, `product_learning_*` consent flags. The Governance tenant registry is authoritative for identity/lifecycle/coarse entitlement classification only — it must never become a replica of tenant business data, PII, secrets, behavioral state, or financial-provider state. `lib/tenantRegistry.js`'s SQL must use an **explicit column allow-list**, never `SELECT *` filtered after the fact — a future column added to `tenants` must be invisible to this route by default, not opt-out.
2. **Platform tenant visibility — locked**: include the one `tenant_kind = 'platform'` row in the list, unfiltered, so the registry stays a truthful projection of the real table. Visibility does not imply mutability: any future tenant-management mutation phase (1A.8 commissioning, suspend/decommission, etc.) must add an explicit reserved-tenant guard that fails closed for `tenant_kind = 'platform'` unless the master plan explicitly names an exception. Not this phase's concern to build (1A.7 has no mutation route at all), but recorded here so 1A.8 doesn't have to rediscover it.
3. **Slug lookup — locked**: `GET /tenants/:identifier` resolves by `tenants.id` when the path segment is a valid UUID, otherwise by exact `tenants.slug` (confirmed `unique` with a supporting index at `migrations/001_tenants_foundation.sql:15,42`, untouched by any later migration). No fuzzy/partial/case-insensitive matching. The response always carries the canonical `id` regardless of which form was used to look it up. Unknown UUID or slug both produce the identical 404 shape — no distinguishing error that could leak which form was attempted. Both forms require the same `tenants.read` scope; slug is purely an addressing convenience, not a second identity — internal references, audit rows, and any future mutation continue to key on `id` only, and slug is not assumed stable over time by anything except this one lookup route.

**Freshness envelope (§61), concretely**: every response carries `observedAt` (the read timestamp), `source: "infrakinetic-live"`, and `freshness: "live"` — no cache, no staleness state machine in this phase (that's 1A.10's reconciliation concern, which is about desired-vs-effective drift, not registry currency).
