## The vertical, end to end

```
authenticated operator (Governance's own /management/v1/engine-state/:engineKey, human-facing)
  -> requireScope("engines.platform_state.write") [Governance's own 1A.2 authz]
  -> requestEngineStateChange() [new orchestration, Governance]
       -> GET  /management/v1/engines/:key/state   (resolve alias, capture before-state)  [real assertion #1]
       -> 1A.5 createOrReplayOperation()            (idempotency reservation + ledger entry)
       -> PUT  /management/v1/engine-state/:key     (real setPlatformEngineState())        [real assertion #2]
       -> GET  /management/v1/engines/:key/state    (independent effective observation)    [real assertion #3]
       -> 1A.5 transitionOperation() -> completed | partially_completed | failed
```

Three separate, single-use (jti) assertions per real (non-replay) call — one per hop — never one assertion reused
across steps. On replay, only the first GET (read-only, harmless) runs; the PUT and the post-mutation GET are never
repeated, which is what makes "`setPlatformEngineState()` called exactly once for idempotent retry" true by
construction rather than by a retry counter.

## Idempotency semantics (instruction #8)

`canonicalHash.ts`'s scope already binds `{requestedAction, targetTenantId, targetEngine, payload}` together (built
in 1A.5); `engineStateOperation.ts` puts `{desiredState, metadata, recoveryIntent, rollbackOfOperationId}` into that
payload, so a reused idempotency key with a different engine, different desired state, or materially different
metadata/payload all produce a different hash and are rejected as a conflict — proven live below (different desired
state) and in `engineStateOperation.test.ts` (different engine, different desired state, both explicitly).

`assertion replay protection != operation idempotency` (instruction #8's own framing) — both axes were exercised
separately live: the 1A.4 jti-replay guard (unchanged code) rejects a second use of the *same signed assertion*
regardless of what it requests; 1A.5's ledger rejects/replays based on the *idempotency key + payload hash*,
independent of which (single-use) assertion carried the request.

## Unexpected issue found and fixed during this phase

The first version of `engineStateOperation.ts` built every Infrakinetic-facing path (`/engines/:key/state`,
`/engine-state/:key`) **without** the `/management/v1` prefix — a bug that was entirely invisible to the local test
suite, because the hand-built fake Infrakinetic test double matched the same (wrong) paths the code called, so both
sides were self-consistently wrong. It surfaced immediately during this phase's own read-only blast-radius check (a
real call against the real deployed server, before any mutation was attempted): the request landed on Infrakinetic's
general customer-facing router instead of `/management/v1/*` and was correctly rejected by unrelated middleware. No
mutation was ever attempted with the buggy paths. Fixed by adding a single `MANAGEMENT_V1_PREFIX` constant, all three
call sites corrected, the test double's matching regexes corrected to match, full suite re-run (218/218), rebuilt,
redeployed, and only then was the real live mutation attempted. Recorded here as exactly the kind of finding
instruction #12's "read-only blast-radius assessment before the live test" exists to catch.
