## Database isolation proof (corrected 2026-09-11 — read this version, not any earlier draft)

A brand-new Postgres role is not automatically able to read or write any
existing table — Postgres denies table-level DML by default — but it CAN
by default **connect** to every existing database on the instance:
`CONNECT` is granted to the `PUBLIC` pseudo-role on every database unless
explicitly revoked, and every role is implicitly a member of `PUBLIC`.

**An earlier draft of this document, and the provisioning script it
described, got the fix for this wrong**: it issued
`REVOKE CONNECT ON DATABASE polynoveacrm FROM governance_app` and treated
that as proof of isolation. PostgreSQL privilege resolution is additive —
a role has a privilege if it holds it *directly* or *via `PUBLIC`*.
`governance_app` was never granted `CONNECT` directly; whatever access it
had could only ever have come from `PUBLIC`. Revoking a privilege
`governance_app` never held directly is a no-op — it does not touch
`PUBLIC`'s own grant, and does not change `governance_app`'s effective
access at all. The same reasoning applies to the "belt-and-suspenders"
`REVOKE ALL ON SCHEMA public`/tables/sequences/functions statements an
earlier draft of the provisioning script issued against `polynoveacrm` —
also no-ops for the same reason, also removed.

**Corrected mechanism:**

- For the *new* `polynovea_governance` database, `001` correctly locks
  `PUBLIC` out at creation time (`REVOKE ALL ON DATABASE
  polynovea_governance FROM PUBLIC`, then an explicit `GRANT CONNECT ...
  TO governance_app`) — safe here because the database has no other
  connections or dependents at the moment it is created.
- For the *existing*, shared `polynoveacrm`, `001` makes **no** ACL change
  at all — a blind `PUBLIC` revoke against a live, shared production
  database could break other legitimate access with no isolation gained
  (`governance_app` never had real access there regardless, since it was
  only ever inherited via `PUBLIC`, same as everyone else).
- Instead, `002_verify_cross_database_isolation.sql` is a mandatory,
  read-only live gate: it uses `has_database_privilege()`/
  `has_table_privilege()`/`has_function_privilege()` — the Postgres
  functions that report *effective* privilege, correctly accounting for
  `PUBLIC` and role membership — and fails closed (`RAISE EXCEPTION`) if
  `governance_app` can effectively `CONNECT` to `polynoveacrm`, holds any
  administrative role attribute, or has any role membership. If it fails,
  the required fix is *not* a guessed `governance_app`-specific revoke —
  it is inventorying every legitimate role that needs `polynoveacrm`,
  revoking `CONNECT` from `PUBLIC` there, and explicitly re-granting the
  legitimate roles, as a separately-reviewed production ACL change.

Neither script has been run — see "Live certification required" below.

### pg-mem limitations encountered and worked around (tooling, not application bugs)

- `CREATE TABLE IF NOT EXISTS` fails pg-mem's AST-coverage check when the
  table already exists.
- **`information_schema.tables.table_schema` always reports `'public'` in
  pg-mem, regardless of a table's real schema** (confirmed by direct
  probe — `pg_namespace`/`pg_class` joins are similarly non-functional).
  Real Postgres reports this correctly. Consequence: `ensureMigrationsTable()`
  uses create-then-tolerate-already-exists instead of a schema-filtered
  existence check; tests that assert on `information_schema.tables` query
  without a `table_schema` filter. **This means pg-mem cannot certify true
  schema membership** — that the tables genuinely live in `governance` and
  not `public` — only that the qualified DDL is valid and resolves
  correctly for DML (also independently confirmed by probe: same-named
  tables in two different schemas coexist without collision). Real schema
  membership must be confirmed against the live database.
- `operator_sessions.session_id` is `UUID`, matching real usage — tests use
  UUID-shaped session ids throughout.
