## Database isolation proof (why "zero grants" alone is not sufficient)

A brand-new Postgres role is not automatically able to read or write any
existing table — Postgres denies table-level DML by default — but it CAN
by default **connect** to every existing database on the instance:
`CONNECT` is granted to the `PUBLIC` pseudo-role on every database unless
explicitly revoked, and every role is implicitly a member of `PUBLIC`.
"We never granted `governance_app` anything on `polynoveacrm`" is therefore
not, by itself, proof of isolation — it proves `governance_app` cannot read
or write Infrakinetic's tables, but not that it cannot open a session
against that database at all. The provisioning script closes this
explicitly:

```sql
REVOKE CONNECT ON DATABASE polynoveacrm FROM governance_app;
```

plus, as belt-and-suspenders inside `polynoveacrm` itself in case `CONNECT`
is ever mistakenly re-granted later:

```sql
REVOKE ALL ON SCHEMA public FROM governance_app;
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM governance_app;
REVOKE ALL ON ALL SEQUENCES IN SCHEMA public FROM governance_app;
REVOKE ALL ON ALL FUNCTIONS IN SCHEMA public FROM governance_app;
```

These are documented, not yet executed — see "Live certification required"
below for what must be captured, verbatim, once a real connection exists.

### pg-mem limitations encountered and worked around (tooling, not application bugs)

- `CREATE TABLE IF NOT EXISTS` fails pg-mem's AST-coverage check when the
  table already exists.
- **`information_schema.tables.table_schema` always reports `'public'` in
  pg-mem, regardless of a table's real schema** (confirmed by direct
  probe — `pg_namespace`/`pg_class` joins are similarly non-functional).
  Real Postgres reports this correctly. Consequence: `ensureMigrationsTable()`
  uses create-then-tolerate-already-exists instead of a schema-filtered
  existence check; tests that assert on `information_schema.tables` query
  without a `table_schema` filter. **This means pg-mem cannot certify true
  schema membership** — that the tables genuinely live in `governance` and
  not `public` — only that the qualified DDL is valid and resolves
  correctly for DML (also independently confirmed by probe: same-named
  tables in two different schemas coexist without collision). Real schema
  membership must be confirmed against the live database.
- `operator_sessions.session_id` is `UUID`, matching real usage — tests use
  UUID-shaped session ids throughout.
