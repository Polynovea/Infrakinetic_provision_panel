### Platform-specific finding: `CREATE SCHEMA ... AUTHORIZATION` needs `SET ROLE`

`001`'s `CREATE SCHEMA governance AUTHORIZATION governance_app` failed on
first attempt: `error: must be able to SET ROLE "governance_app" (42501)`.
Cause: AWS RDS's master user is granted `rds_superuser`, not true
PostgreSQL `SUPERUSER` — `rolsuper` is false for `polynovea2021` on this
instance — so the usual superuser bypass for `CREATE ... AUTHORIZATION
<other role>` does not apply. Fixed with a minimal, transactional bracket
around the exact same statement already in `001` (no new capability
granted beyond what the statement needed):

```sql
BEGIN;
GRANT governance_app TO polynovea2021;
CREATE SCHEMA governance AUTHORIZATION governance_app;
REVOKE governance_app FROM polynovea2021;
COMMIT;
```

Verified immediately after: zero rows in `pg_auth_members` involving
`governance_app` in either direction (no lasting membership from the
temporary grant); `governance` schema owner is `governance_app`.

The `governance_app` password generated for the first `CREATE ROLE` was
lost when that run errored on the schema step before it could be
persisted (persistence was gated on full-script success). Reset via

### TLS trust fix required for the real migration runner

`npm run db:migrate` (the actual, reviewed migration runner — not a
substitute script) initially failed with `self-signed certificate in
certificate chain`: `pgDbClient.ts` hardcodes
`rejectUnauthorized: true` when SSL is enabled, but Node does not trust
AWS RDS's CA chain by default, and the client reaches the server through
a local SSH-tunnel address (`127.0.0.1:5433`) rather than the real
hostname the server's certificate was issued for
(`polynovea.cxooososo85k.ap-south-1.rds.amazonaws.com`). Fixed properly,
without weakening verification: `dbConfig.ts`/`pgDbClient.ts` gained two
new optional settings, `GOVERNANCE_DB_SSL_CA_FILE` (a trusted CA bundle —
the Amazon RDS combined bundle is committed at
`backend/certs/rds-ca-global-bundle.pem`, since it is public trust
material, not a secret) and `GOVERNANCE_DB_SSL_SERVERNAME` (the real
hostname to verify the certificate against, overriding the tunnel
address used for the actual TCP connection). `rejectUnauthorized: true`
is unconditional whenever SSL is enabled — never relaxed. 6 new tests
added covering SSL disabled, SSL enabled with a CA file, servername
passthrough, and fail-closed behavior when the configured CA file cannot
be read; full suite after the change: **97/97 tests pass**, typecheck and
lint clean (source + test). With `GOVERNANCE_DB_SSL_CA_FILE`/
`_SERVERNAME` set, the real migration runner connects successfully with
full certificate verification.

## Bootstrap/admin credential — decided

It is acceptable to use the existing privileged RDS master/admin identity
(`polynovea2021`) for the ONE-TIME `CREATE ROLE`/`CREATE DATABASE`/`CREATE
SCHEMA` bootstrap, **provided its actual effective authority on this RDS
instance is verified before relying on it** (i.e. confirm it can really
run `CREATE ROLE`/`CREATE DATABASE` — RDS's master user typically can via
the `rds_superuser`-equivalent role, but this has not been independently
confirmed against the live instance in this session, since this session
cannot reach it). Used only for bootstrap; never becomes
`GOVERNANCE_DB_USER`/`PASSWORD`; its password is never committed. After
bootstrap, every subsequent Governance operation (migrations, runtime)
connects as `governance_app` only. The fact that this account is also
Infrakinetic's own runtime credential is tracked separately as `BL-7`, not
remediated as part of this subphase.

## Database isolation proof (corrected 2026-09-11 — read this version, not any earlier draft)

A brand-new Postgres role is not automatically able to read or write any
existing table — Postgres denies table-level DML by default — but it CAN
by default **connect** to every existing database on the instance:
`CONNECT` is granted to the `PUBLIC` pseudo-role on every database unless
explicitly revoked, and every role is implicitly a member of `PUBLIC`.

**An earlier draft of this document, and the provisioning script it
described, got the fix for this wrong**: it issued
`REVOKE CONNECT ON DATABASE polynoveacrm FROM governance_app` and treated
that as proof of isolation. PostgreSQL privilege resolution is additive —
a role has a privilege if it holds it *directly* or *via `PUBLIC`*.
`governance_app` was never granted `CONNECT` directly; whatever access it
had could only ever have come from `PUBLIC`. Revoking a privilege
`governance_app` never held directly is a no-op — it does not touch
`PUBLIC`'s own grant, and does not change `governance_app`'s effective
access at all. The same reasoning applies to the "belt-and-suspenders"
`REVOKE ALL ON SCHEMA public`/tables/sequences/functions statements an
earlier draft of the provisioning script issued against `polynoveacrm` —
also no-ops for the same reason, also removed.

**Corrected mechanism:**

- For the *new* `polynovea_governance` database, `001` correctly locks
  `PUBLIC` out at creation time (`REVOKE ALL ON DATABASE
  polynovea_governance FROM PUBLIC`, then an explicit `GRANT CONNECT ...
  TO governance_app`) — safe here because the database has no other
  connections or dependents at the moment it is created.
- For the *existing*, shared `polynoveacrm`, `001` makes **no** ACL change
  at all — a blind `PUBLIC` revoke against a live, shared production
  database could break other legitimate access with no isolation gained
  (`governance_app` never had real access there regardless, since it was
  only ever inherited via `PUBLIC`, same as everyone else).
- Instead, `002_verify_cross_database_isolation.sql` is a mandatory,
  read-only live gate: it uses `has_database_privilege()`/
  `has_table_privilege()`/`has_function_privilege()` — the Postgres
  functions that report *effective* privilege, correctly accounting for
  `PUBLIC` and role membership — and fails closed (`RAISE EXCEPTION`) if
  `governance_app` can effectively `CONNECT` to `polynoveacrm`, holds any
  administrative role attribute, or has any role membership. If it fails,
  the required fix is *not* a guessed `governance_app`-specific revoke —
  it is inventorying every legitimate role that needs `polynoveacrm`,
  revoking `CONNECT` from `PUBLIC` there, and explicitly re-granting the
  legitimate roles, as a separately-reviewed production ACL change.

Neither script has been run — see "Live certification required" below.

- `CREATE TABLE IF NOT EXISTS` fails pg-mem's AST-coverage check when the
  table already exists.

  pg-mem, regardless of a table's real schema** (confirmed by direct
  probe — `pg_namespace`/`pg_class` joins are similarly non-functional).

  not `public` — only that the qualified DDL is valid and resolves
