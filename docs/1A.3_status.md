# 1A.3 — Governance DB — status

Date: 2026-09-11

## Scope decision made this subphase

The master plan's §64 "1A.3 — Governance DB" deliverable is: separate
Postgres DB; separate role; migrations; base ledger/idempotency schema.
Exit: Governance backend can access its own DB; zero grants on
Infrakinetic DB.

1A.2's own status doc explicitly pre-announced how 1A.3 should land: "the
adapter seam is designed so 1A.3 swaps in Postgres-backed implementations
without touching the middleware, routes, or any test above the adapter
layer." This subphase does exactly that — `PostgresOperatorDirectory` and
`PostgresSessionStore` now implement the same `OperatorDirectory`/
`OperatorSessionStore` ports the in-memory 1A.2 adapters implemented, and
`src/index.ts` wires them in as the default. Neither
`requireManagementApiAuth`, `authorize.ts`, nor `createManagementRouter`
changed — every 1A.2 test above the adapter layer still passes unmodified.

## Built, local only

- **Migration `0002_governance_db_foundation.sql`** — adds
  `management_idempotency_keys` (master plan §59) and `operator_audit_log`
  (base shape of the immutable action ledger, §19 — distinct from 0001's
  narrower `operator_auth_audit_log`, which only records
  authentication/authorization decisions, not privileged actions). No
  application code writes to `operator_audit_log` yet — there is no
  privileged mutation route to write from until 1A.4/1A.6; wiring every
  mutation to it is 1A.5's deliverable, matching 1A.2's own established
  precedent for `ConsoleAuditSink`/`InMemoryAuditSink` (a schema-ready seam
  1A.5 replaces).
- **Correction to 0001, in the same migration**: relaxed
  `operator_sessions.operator_id/issued_at/expires_at` from `NOT NULL` to
  nullable. Building `PostgresSessionStore` against the actual
  `OperatorSessionStore` port surfaced a real design constraint: 1A.2 never
  mints a separate management assertion with its own issuance event — a
  "session" is just the verified Cognito token's own `jti`, and
  `revoke()`/`recordStepUp()` (the only two writes the port exposes) may be
  the *first* write ever made for a given session id, with no operator id,
  issued-at, or expiry available to either call. The strict `NOT NULL` made
  the literal 1A.2 contract impossible to satisfy through the adapter alone
  without changing the port/middleware signatures — which 1A.2's own status
  doc says 1A.3 must not do. Relaxed rather than widened the port; documented
  in full in the migration file itself. Verified via pg-mem
  (`test/migrations/0002_governance_db_foundation.test.ts`).
- **DB connection layer** (`src/db/`):
  - `dbConfig.ts` — `GOVERNANCE_DB_*` loader, same "required env var, thrown
    lazily, never at import time" pattern as `identity/cognitoConfig.ts`.
  - `dbClient.ts` — minimal `DbClient` query interface (not the full
    `pg.Pool` API), satisfied both by a real `pg.Pool` (`pgDbClient.ts`) and,
    in tests, by pg-mem's pg-compatible adapter
    (`newDb().adapters.createPg()`) — the same "real code, substituted
    transport" technique 1A.2 used for Cognito JWT verification against a
    local JWKS instead of a network call.
  - `pgDbClient.ts` — real Postgres-backed `DbClient`; wraps every
    query failure as a typed `DatabaseUnavailableError` (503,
    `GOVERNANCE_DB_UNAVAILABLE`) rather than letting a raw driver error
    surface.
  - `lazyDbClient.ts` — defers construction (and therefore
    `GOVERNANCE_DB_*` validation) until the first real query, mirroring
    `identity/providers/lazyIdentityProvider.ts`. Server boot and
    `/healthz` never require the database to exist.
  - `migrationRunner.ts` — applies `backend/migrations/*.sql` in filename
    order, tracked in a `schema_migrations` table, skipping
    already-applied files. Idempotent re-run is a safe no-op. **Not
    transactional** across statements or files (documented limitation —
    the minimal `DbClient` interface has no cross-call transaction
    primitive; acceptable for 1A.3's own two small, additive-only
    migrations, flagged for hardening before this runner is trusted with
    a migration where partial application would matter).
  - `errors.ts` — `DatabaseUnavailableError`, a `ManagementAuthError`
    subclass so a DB outage flows through the exact same typed,
    audited, deny-by-default path every other dependency failure already
    uses in this codebase (compare `ConfigurationError` for the equivalent
    Cognito-side case).
- **`scripts/migrate.ts`** (`npm run db:migrate [-- --dry-run]`) — explicit,
  operator-invoked CLI, no HTTP surface, same posture as
  `scripts/bootstrapOperator.ts`.
- **Postgres-backed identity adapters**
  (`src/identity/adapters/postgresOperatorDirectory.ts`,
  `postgresSessionStore.ts`) — implement the exact 1A.2 ports against the
  0001/0002 schema. `PostgresSessionStore.revoke()`/`recordStepUp()` use
  `INSERT ... ON CONFLICT (session_id) DO UPDATE` (UPSERT), not `UPDATE`,
  because — per the correction above — no prior row is guaranteed to exist.
- **`src/index.ts` rewiring** — `operatorDirectory`/`sessionStore` are now
  `PostgresOperatorDirectory`/`PostgresSessionStore` over a
  `LazyDbClient(() => PgDbClient.fromEnv())`, replacing the 1A.2
  fixture-seeded in-memory adapters. `config/operators.seed.json` and the
  file-based bootstrap flow it supported are no longer the live wiring as
  a result (see "Deliberately not done" below). `/healthz` now reports
  `phase: "1A.3"`.
- **Provisioning script** (`backend/provisioning/001_create_role_and_database.sql`
  + `backend/provisioning/README.md`) — creates the dedicated
  `governance_app` role (`LOGIN`, `NOSUPERUSER`/`NOCREATEDB`/`NOCREATEROLE`)
  and the `polynovea_platform_governance` database it owns. Authored with
  an intentionally-invalid placeholder password so it cannot be run
  unmodified. One role, not a separate migration-owner/runtime-DML split —
  documented as a reasonable future hardening (loosely tracked against
  1A.19), not required to satisfy this subphase's literal exit criteria,
  and not built speculatively.

## Deliberately not done

- **No Governance database exists anywhere.** This session has no reachable
  Postgres server — not RDS (no AWS credentials, same capability gap
  documented in `docs/1A.2_status.md`), and no *local* Postgres either
  (`psql`, `pg_ctl`, `postgres` are all absent from PATH; `docker` is not
  installed). This is a strictly worse position than 1A.2's, which at
  least had *a plan* to reach a real Postgres eventually via an RDS tunnel
  — here there is no reachable Postgres server of any kind in this
  environment. See "DB/AWS provisioning required to finish live 1A.3"
  below.
- **The provisioning script has never been run.** No role, no database,
  anywhere.
- **`scripts/bootstrapOperator.ts` was not extended to write to Postgres.**
  It still only writes `config/operators.seed.json`, which is no longer
  read by `src/index.ts`. Extending it to a DB-backed mode is a reasonable,
  low-risk follow-up, but real operator bootstrap execution is explicitly
  sequenced at 1A.18 (per your instruction this session — "Do NOT bootstrap
  a special internal tenant now... Keep `bootstrapOperator.ts`; it is the
  correct controlled mechanism"), so extending it now would be speculative
  scope with nothing to exercise it against. Left undone on purpose, not
  forgotten.
- **No transactional migrations.** See `migrationRunner.ts`'s own comment;
  restated here because it is a real limitation, not just an implementation
  note.
- **No RLS.** Evaluated and deliberately not built: every table this
  subphase adds (`operators`/`operator_roles`/`operator_scopes`/
  `operator_sessions`/`operator_auth_audit_log` from 0001;
  `management_idempotency_keys`/`operator_audit_log` from 0002) is
  fleet-wide platform-operator data, not per-tenant data — there is no
  tenant partitioning concern for RLS to enforce at this subphase, unlike
  Infrakinetic's own multi-tenant tables. The isolation boundary at 1A.3 is
  DB/role-level instead: a dedicated `governance_app` role with zero grants
  on any Infrakinetic database (provable by the total absence of any
  Infrakinetic-database reference in `provisioning/001_create_role_and_database.sql`
  or anywhere else in this repository), not row-level policy within one
  shared table. RLS becomes relevant again once a table carries a
  `tenant_id`/`responsible_operator` column meant to scope query results
  per caller — not yet the case for anything 1A.3 introduces. Revisit at
  whichever later subphase first adds such a table.
- **No connection pooling infrastructure** (PgBouncer, RDS Proxy) — not a
  1A.3 deliverable per the master plan's own §64 scope.

### Fail-closed proof for the DB layer specifically (not just live-boot)

Because this session cannot reach any real Postgres server, the "database
unavailable" HTTP path (as opposed to "Cognito unavailable", which live-boot
already proves) is proven by test, not by curl:
`test/db/managementApiAuthDbUnavailable.integration.test.ts` wires a real
Express router (`createManagementRouter`) with a structurally-valid signed
token (via the same local-JWKS technique 1A.2 uses for all Cognito tests)
and an `operatorDirectory` that throws `DatabaseUnavailableError`, and
confirms the response is a clean `503 GOVERNANCE_DB_UNAVAILABLE` — not a
500, not a hang, no operator context in the body.

### pg-mem limitations encountered and worked around (tooling, not application bugs)

- `CREATE TABLE IF NOT EXISTS` fails pg-mem's AST-coverage check when the
  table already exists (a documented pg-mem rough edge, not a real Postgres
  restriction). `ensureMigrationsTable()` was written as an explicit
  existence check + plain `CREATE TABLE` instead — equally correct against
  real Postgres, and sidesteps the limitation entirely. See
  `migrationRunner.ts`'s comment.
- `operator_sessions.session_id` is `UUID`, matching real usage (a verified
  Cognito token's `jti`, which is UUID-shaped) — a first draft of the
  session-store tests used non-UUID literal strings like `"session-a"` and
  failed identically against pg-mem and would fail identically against real
  Postgres (`invalid input syntax for type uuid`). Not a pg-mem-only quirk;
  fixed by using UUID-shaped test session ids throughout.

## Is 1A.4 genuinely blocked on live 1A.3?

**Partially, and in the same shape 1A.2's status doc described for its own
downstream dependency.** 1A.4 ("Management API transport and read-only
contract") needs the request/response shape and scope-enforcement machinery
this subphase did not touch — that work is independent of whether a real
Postgres database exists yet. But per 1A.2's own scope decision (still
unresolved as of this subphase — see `docs/1A.2_status.md` "Scope decision
made this subphase"), if 1A.4 means extending *this* repository's
read-contract surface, any endpoint that resolves through
`operatorDirectory`/`sessionStore` now depends on the same live-database
gap this subphase documents — the code path is ready, proving it end-to-end
against a real request needs the same infrastructure step. If 1A.4 is the
Infrakinetic-side `/management/v1/*` surface in the other repository, it is
unaffected by this subphase's local-only status.

**1A.6 ("first real vertical: platform engine state") is more clearly
gated**: it is the first subphase expected to write real rows into the
ledger/idempotency tables 1A.3 just created, so it needs a real database to
mean anything beyond schema validation.
