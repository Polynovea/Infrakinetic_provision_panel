## Architecture correction — 2026-09-11

**An earlier version of this document, and the code it described, assumed
1A.3 meant provisioning a separate Postgres database for Governance.** That
assumption was wrong and has been explicitly corrected:

> Phase 1A Governance uses the SAME existing production Postgres database
> as Infrakinetic (`polynoveacrm`, on the existing RDS instance). It does
> not get its own database. Isolation is a dedicated schema (`governance`)
> owned by a dedicated role (`governance_app`), not database-level
> separation.

This changes the master plan's §18/§64 "1A.3" text too — both have been
annotated with the same correction (see
`docs/Infrakinetic Document/Architecture Plan Docx/Engine Overhauls/Phase1A_Polynovea_Platform_Governance_Extended_Master_Plan_2026-09-10_v2.md`
in the Infrakinetic repository).

What changed as a result, all reconciled in this same pass, before any live
provisioning was attempted:

- `backend/provisioning/001_create_role_and_database.sql` → renamed
  `001_create_role_and_schema.sql`. No longer runs `CREATE DATABASE`;
  creates `governance_app` (`NOSUPERUSER`/`NOCREATEDB`/`NOCREATEROLE`/
  `NOBYPASSRLS`/`NOINHERIT`) and `CREATE SCHEMA governance AUTHORIZATION

  table-level DML by default, so a role with nothing explicitly granted to

- Migrations `0001_operator_identity_schema.sql` and

- `src/identity/adapters/postgresOperatorDirectory.ts` and

## Deliberately not done

- **No live provisioning was attempted.** `governance_app`/`governance`
  schema exist nowhere. This session re-verified it has no reachable
  Postgres server — not RDS (no AWS credentials), and no *local* Postgres
  either (`psql`, `pg_ctl`, `postgres` absent from PATH; `docker` not
  installed) — and did not attempt to install or provision anything
  without being asked to. See "DB/AWS provisioning required to finish live
  1A.3" below.
- **`scripts/bootstrapOperator.ts` was not extended to write to Postgres.**
  It still only writes `config/operators.seed.json`, which is no longer
  read by `src/index.ts`. Extending it to a DB-backed mode is a reasonable,
  low-risk follow-up, but real operator bootstrap execution is explicitly
  sequenced at 1A.18 ("Do NOT bootstrap a special internal tenant now...
  Keep `bootstrapOperator.ts`; it is the correct controlled mechanism"), so
  extending it now would be speculative scope with nothing to exercise it
  against. Left undone on purpose, not forgotten.
- **No transactional migrations.** See `migrationRunner.ts`'s own comment;
  restated here because it is a real limitation, not just an implementation
  note.
- **No RLS.** Evaluated and deliberately not built: every table this
  subphase adds (`governance.operators`/`operator_roles`/`operator_scopes`/
  `operator_sessions`/`operator_auth_audit_log` from 0001;
  `management_idempotency_keys`/`operator_audit_log` from 0002) is
  fleet-wide platform-operator data, not per-tenant data — there is no
  tenant partitioning concern for RLS to enforce at this subphase, unlike
  Infrakinetic's own multi-tenant tables. The isolation boundary at 1A.3 is
  schema/role-level instead: a dedicated `governance_app` role, owning and
  confined to the `governance` schema, with zero grants on `public` or any
  Infrakinetic table (provable by the total absence of any such grant in
  `provisioning/001_create_role_and_schema.sql` or anywhere else in this
  repository — not by a different database). RLS becomes relevant again
  once a table carries a `tenant_id`/`responsible_operator` column meant to
  scope query results per caller — not yet the case for anything 1A.3
  introduces. Revisit at whichever later subphase first adds such a table.
- **`PUBLIC`'s default schema grant on `public` was not revoked.** A
  database-wide security-posture change affecting every current and future
  role on the shared instance, not scoped to `governance_app` alone, and
  not required for its isolation (`USAGE` alone does not grant table-level
  DML) — see the provisioning script's own trailing comment. Left as a
  documented, explicitly-not-done optional hardening.
- **No connection pooling infrastructure** (PgBouncer, RDS Proxy) — not a
  1A.3 deliverable per the master plan's own §64 scope.

### pg-mem limitations encountered and worked around (tooling, not application bugs)

- `CREATE TABLE IF NOT EXISTS` fails pg-mem's AST-coverage check when the
  table already exists (a documented pg-mem rough edge, not a real Postgres
  restriction).
- **`information_schema.tables.table_schema` always reports `'public'` in
  pg-mem, regardless of the table's real schema.** Confirmed by direct
  probe: `CREATE SCHEMA governance; CREATE TABLE governance.foo (...)`
  correctly isolates data (`SELECT * FROM governance.foo` and
  `SELECT * FROM public.foo` are genuinely different tables — a
  same-named table can exist in both schemas simultaneously without
  collision), but `information_schema.tables` labels `foo` as
  `table_schema: 'public'` either way. `pg_catalog.pg_namespace` and a
  `pg_class`/`pg_namespace` join are similarly non-functional in pg-mem
  (return zero rows). This is a real pg-mem introspection gap, not a real
  Postgres restriction — **real Postgres reports `table_schema` correctly**.
  Consequences, both handled:
  - `ensureMigrationsTable()` was rewritten from "check via
    `information_schema.tables WHERE table_schema = 'governance'`, then
    create" to "create, then tolerate an 'already exists' error" — this
    sidesteps the pg-mem gap entirely *and* is strictly safer against a
    real database (no check-then-create race). See `migrationRunner.ts`'s
    comment for the full reasoning.
  - Every test that asserts on `information_schema.tables` now queries
    without a `table_schema` filter (proving the tables exist and the
    qualified DDL is valid) rather than asserting `table_schema =
    'governance'` (which pg-mem cannot report correctly). **This means
    true schema isolation — that these tables genuinely live in
    `governance` and not `public` — is not, and cannot be, certified by
    this session's pg-mem-based test suite.** It is certified by direct
    reference to the migration files' own explicit `governance.` prefixes
    (which pg-mem *does* correctly resolve and enforce for DML, per the
    probe above) and must be independently re-confirmed against the real
    database during live certification (see the checklist below).
- `operator_sessions.session_id` is `UUID`, matching real usage (a verified
  Cognito token's `jti`, which is UUID-shaped) — session-store tests use
  UUID-shaped test session ids throughout for this reason.
