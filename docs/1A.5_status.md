## Idempotency semantics — `managementOperationLedger.ts`

`createOrReplayOperation()`:

1. Validates synchronously (idempotency key present, risk class known,
   reason present when the risk class requires one) before any query runs.
2. Computes `safePayloadHash` (`canonicalHash.ts`) over
   `{requestedAction, targetTenantId, targetEngine, payload}` together —
   not the payload alone — so a key reused with a different action, tenant,
   engine, *or* payload is detected as a conflict; none of those four can
   silently alias to the same operation (instruction #6).
3. Attempts a **plain INSERT** (no `ON CONFLICT`) into
   `management_idempotency_keys`. Its `PRIMARY KEY` on `idempotency_key`
   is what makes two concurrent callers racing the same key resolve
   correctly at the database level — not an application-level
   `SELECT`-then-`INSERT` (instruction #11). The loser observes a
   unique-violation, not a race it has to reason about itself.
4. On success (reservation won): inserts the `management_operations` row
   and its initial `'submitted'` ledger event in one transaction (both or
   neither).
5. On failure (someone already holds the key): re-reads the recorded
   `request_hash`. Different hash → `IdempotencyConflictError` (409). Same
   hash → this is either a genuine replay or a concurrent identical
   request that lost the reservation race by microseconds; a short bounded
   retry (up to 5 × 5 ms) waits for the winner's operation row to become
   visible, then returns it with `replay: true`. Never fabricates a result.

One implementation note worth recording: this deliberately does **not**
use `INSERT ... ON CONFLICT DO NOTHING RETURNING` to detect the
winner/loser. That combination proved unreliable under pg-mem (it returned
the attempted row even when the insert was skipped) and, independently,
a failed statement inside a multi-statement transaction poisons the rest
of that transaction in real Postgres without a `SAVEPOINT`. The reservation
attempt is therefore its own standalone (autocommit) statement, and a
unique-violation is detected by matching Postgres's own standard error
wording (`wrapDbError` in `db/pgDbClient.ts` discards the driver's error
code, keeping only the message).

`transitionOperation()` is guarded by `WHERE status = <last-observed
status>`, so a concurrent transition of the same operation between read and
write is detected (0 rows updated → `ConcurrentTransitionConflictError`)
rather than silently overwritten.

Proven (local, `test/management/operations/managementOperationLedger.test.ts`
and `syntheticCertification.test.ts`): same-key/same-payload replay returns
the identical operation with no second row created; same-key/different-payload,
different-action, or different-target all reject as conflicts; concurrent
`Promise.all` calls with the same key collapse to exactly one durable row;
a fresh service instance over the same store ("process recreation") still
sees prior state. Proven live: identical behavior against the real deployed
backend and real database (see "Live certification" below).

## Lifecycle — `lifecycle.ts`

The full 7-state graph (`submitted → accepted → running →
{partially_completed | completed | failed}`, `partially_completed →
{compensating | completed | failed}`, `compensating → {completed | failed}`)
with both terminal states having zero outgoing edges. Every transition not
in the adjacency list — skipping a stage, moving backwards, or leaving a
terminal state — fails closed as `InvalidLifecycleTransitionError`.

## Safe evidence snapshots — `evidence.ts`

`buildSafeSnapshot()` produces a bounded (max depth 8, arrays truncated to
50 elements), versioned (`EVIDENCE_SNAPSHOT_VERSION`), hashable
(`sha256` over the canonicalized safe data) envelope. Redaction runs on
every snapshot and on `approval_evidence`/`rollback_reference` before they
ever reach a query parameter: any key matching a secret-shaped pattern
(`password`, `secret`, `token`, `api[_-]?key`, `private[_-]?key`,
`credential`, `pem`, `authorization`, `cookie`, `otp`, `mfa[_-]?code`) is
replaced with `[redacted]`, and so is any *value* that looks like a PEM
block or a JWT regardless of its key name — a defense the key-name filter
alone would miss.
