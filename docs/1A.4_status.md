
Distinct facts the assertion carries, never collapsed (master plan §16):
`operator_id`/`operator_session_id` (the human), `actor_tenant_id` (fixed
to `"polynovea-platform-governance"` — the calling *service*, never
caller-influenced), `target_tenant_id` (optional, omitted for the two
platform-wide reads this phase implements), `target_engine`,
`requested_action`, `scopes` (narrowed per call, never the operator's full
grant), `correlation_id`. The RS256 signature itself, verified against
Governance's JWKS, is the "this is really Governance calling" fact — it is
not a claim, so it cannot be forged the way a claim value could be.

## Governance side — what was built (`polynovea-platform-governance/backend/src/management/`)

- `managementConfig.ts` — fixed TTL bounds (60–120s, clamped, never

  config loader in this backend).
- `managementSigningKeys.ts` — loads the active RS256 private key (PEM)
  and derives its own public JWK **from the private key via
  `createPublicKey()`**, not `exportJWK()` on the private key object
  directly — see "Bug found and fixed by this phase's own tests" below.
  Supports an optional JSON array of additional public-only JWKs for a
  rotation grace window.
- `managementAssertionIssuer.ts` — `mintManagementAssertion()`. Rejects
  minting if any requested scope isn't in the operator's own granted
  scopes (never widens); rejects zero-scope requests; clamps TTL.
- `managementJwks.ts` — builds the public JWK Set Infrakinetic fetches.
- `managementApiClient.ts` — the one place Governance would call
  Infrakinetic's `/management/v1/*` (Bearer-attached fetch wrapper). Not
  wired into any real route this phase (no live call happens) — proven via

  key material ever reaches the outbound request.
- `lazyManagementKeys.ts` — same lazy-singleton pattern as
  `lazyDbClient.ts`/`lazyIdentityProvider.ts`.
- `GET /.well-known/management-jwks.json` (wired into `src/index.ts`) —

- `scripts/check_no_signing_key_in_frontend.mjs` (new `npm run
  check:no-signing-key-in-frontend`) — scans `frontend/` for any import of

### Bug found and fixed by this phase's own tests

`managementSigningKeys.ts`'s first draft called `exportJWK(activePrivateKey)`
directly — `jose`'s `exportJWK()` on a **private** key object exports the
private exponent (`d`) into what must be a public-only JWKS. A test
(`test/management/managementSigningKeys.test.ts`, "derives its own public
JWK from the private key") caught this immediately (`expected ... to not
have property "d"` failed) before it ever reached a JWKS endpoint. Fixed
by deriving the public key first via Node's `createPublicKey()`, then
exporting *that*. Recorded here because it is exactly the kind of finding
this document's own convention (1A.3's hardening audit, BL-8) says to
record rather than quietly fix and move on.

## Infrakinetic side — what was built (`CRM/api-server/src/`)

- `middleware/requireManagementApiAuth.js` — the core verifier. Uses this
  codebase's own established `jsonwebtoken` + `jwks-rsa` pattern
  (`lib/cognitoJwt.js`'s precedent), with an injectable `getKey` resolver
  so tests exercise real signature verification against local keys with
  no network call. Checks, in order: Bearer presence, JWS shape,
  signature/issuer/audience/algorithm (via `jsonwebtoken`'s `algorithms:
  ["RS256"]` allow-list — rejects `none`/HS256/anything else), `iat`/`exp`
  presence, TTL ≤ configured max (defense in depth beyond "not yet
  expired" — a forged-far-future `exp` is caught even though it would
  technically still verify), every required claim
  (`jti`/`operator_id`/`operator_session_id`/`roles`/`scopes`/`target_engine`/
  `requested_action`/`correlation_id`), then replay (below). Attaches
  `req.managementContext` — a distinct name from `req.tenantId`/`req.userId`
  (customer-session auth) on purpose. Fails closed; no fallback path.
  Reuses none of: customer session auth, `requirePlatformKey`,
  `master_admin`, legacy internal-admin routes.
- `middleware/requireManagementScope.js` — per-route authorization,
  separate from authentication (mirrors Governance's own
  authorize.ts/requireManagementApiAuth split). Checks both scope
  membership and requested-action/route consistency (master plan §16) —
  a valid assertion minted for one action cannot be replayed against a
  different route.
- `management/managementJwksResolver.js` — `createRemoteManagementKeyResolver()`
  (production, `jwks-rsa`-backed) and `createStaticManagementKeyResolver()`
  (test-only, in-memory, no network).
- `management/managementReplayGuard.js` — `RedisManagementReplayGuard`
  (production; atomic `SET key val NX PX ttlMs`, reusing this codebase's
  existing Redis client from `db/redis.js`, the same primitive shape
  `middleware/rateLimit.js` already established) and
  `InMemoryManagementReplayGuard` (test-only). Applied uniformly to every
  verified assertion, not only future mutation calls — see "Replay
  protection design" below for why.
- `management/managementErrors.js` — typed rejection reasons, mirroring
  Governance's own `identity/errors.ts` code/httpStatus shape (not a
  shared import — no filesystem imports between the repos, per hard rule
  — just a consistent convention).
- `management/managementAuthDeps.js` — production wiring, reads
  `GOVERNANCE_MANAGEMENT_ISSUER`/`_AUDIENCE`/`_JWKS_URI`. Throws a typed
  `ManagementConfigurationError` if any is unset; `src/index.js` catches
  this at mount time and responds `503 MANAGEMENT_API_NOT_CONFIGURED` on
  `/management/v1/*` specifically, rather than crashing server boot —
  same "an unprovisioned dependency fails closed at its own boundary, not
  at boot" posture this whole program (both repos) has followed since
  1A.1.
- `management/managementCommandContract.js` — `management.command`
  envelope validator (§17 shape) + `enqueueManagementCommand()` (thin
  wrapper over the existing outbox). **Scaffold only** — no route calls
  this; no channel handler is registered; there is no mutation endpoint
  anywhere in this phase.
- `routes/management/v1/index.js` — the two read endpoints:
  `GET /engines/catalog` (scope `engines.read`, action
  `engines.catalog.read`) and `GET /engines/:engineKey/state` (scope
  `engines.read`, action `engines.state.read`, 404 on an unresolvable
  engine key before any query runs).
- `src/index.js` — mounts `/management/v1` alongside the other
  pre-`authenticate()` "token resolved server-side" routers (next to
  `/api/external/v1/payroll`, same reasoning as that router's own
  comment), never entering the customer-session/tenant-context middleware
  chain at all.

### Replay protection design (deliberately not 1A.5)

Every assertion `requireManagementApiAuth` accepts is marked single-use via
`jti`, for exactly its own remaining lifetime (60–120s) — cheap, since a
legitimate caller mints a fresh assertion per call anyway. This is
transport/assertion replay protection, not 1A.5's future mutation
idempotency (a business-level "don't apply this command twice" concern,
keyed on an idempotency key, backed by Governance's own
`management_idempotency_keys` table against a real mutation's effects).
Applying it uniformly now — not gated to some future "is this a mutation"
check — means 1A.5/1A.6 inherit single-use enforcement without touching
the assertion format or this middleware at all.
